## 「已登录却取不到信息」故障：长驻 httpx 死连接（12:05-12:20）
- 现象：`/api/me` 正常返回 logged_in=true、uin=0004821992，但 `/api/state` 稳定返回
  `{"ok":false,"code":-1,"message":"连接腾讯服务器失败（网络抖动）"}`；同一时刻用脚本新建
  `LoginSession().restore()` 直接 `post(EP_MAINPAGE)` 却 code=0 成功。
- **根因**：后端全局单例 `_session` 的 `httpx.AsyncClient` 长驻，keep-alive 连接被腾讯服务端
  空闲后单方面关闭，连接池下次仍复用这条死连接 → 每次请求都抛 `httpx.ConnectError`，
  被 `main.py` 的 ConnectError 分支兜底成「网络抖动」。只有重启进程重建 client 才恢复。
  所以「登录态正常但取不到数据」≠ cookie 过期，别往 session 方向排查。
- **修复（backend/mc_api.py）**：
  1. `__init__` 加 `httpx.Limits(max_connections=20, max_keepalive_connections=5)`
     （httpx 0.28.1 参数名是 `max_keepalive_connections`，写 `max_keepalive` 会
     TypeError 导致服务起不来）。
  2. `post()` 包一层 `for attempt in (0,1)`：捕获 `RETRYABLE`
     （ConnectError/ReadError/WriteError/RemoteProtocolError/PoolTimeout）后调
     `_reset_client()`（aclose 旧连接 + 新建 client 并把 cookie 逐个迁移）再重试一次。
- 验证：patch `httpx.AsyncClient.post` 第 1 次抛 ConnectError，实测 attempts=2、result code=0、
  client 已重建、skey 保留 → SELF-HEAL OK。
- 排查经验：脚本单独调成功、服务端端点失败时，优先怀疑**进程内长驻连接池状态**，而不是账号/接口/参数。

## 调研结论：为什么只有「时尚男/女套装」面额序列不是降序（14:00）
- `theme_card_list[i][11]`（卡 id 列表）在原始数据里是**按 card id 降序**存放的（如主题52: 63,62,...,50）。
- 绝大多数套卡的 card id 是开发时按层次连号录入的：150 面额终卡(id最大) → 40 面额中卡 → 10 面额基础卡(id最小)。
  所以「id 降序」在大多数套卡上**恰好等于「面额降序」**，这是巧合，不是排序保证。
- 例外：**时尚男套装(theme 40)** 原套连号 29-39（缺34）追加了 **64/65/66**（银珠裤链/黄色TAXI/黑色提包，均 10 面额）；
  **时尚女套装(theme 45)** 原套连号 40-49 追加了 **67/68/69**（单车/经典包包/M字腰带，均 10 面额）。
  追加卡 id 更大 → 排在降序列表最前面，但它们只有 10 面额 → 序列变成 10,10,10,…,150,40,…
- 量化：全库 1681 个主题里有 46 个 id 序≠面额序；**star=1 共 32 个主题，只有这 2 个（40/45）例外**，与用户观察完全一致。
- 结论：不是数据错误，是「拿 id 顺序当展示顺序」的取巧失效。若要做稳定展示，应按 `price` 降序（同价再按 id 降序）重排，
  而不是沿用原始数据顺序。（尚未修改，待用户确认。）

## 19:00 「又不能显示了」——连接池自愈失效（持续 ConnectError）

现象：`/api/state` 100% 返回「连接腾讯服务器失败（网络抖动）」，前端整页空白；
但 `/api/me` 正常（内存登录态在），同一台机器 curl 通、进程外用相同 httpx 代码请求返回 200。

排查要点（避免下次重复）：
- 先分辨「进程死 / 网络断 / 代码旧 / 进程内状态坏」四类：
  `lsof -i :8000` 看监听 → `curl` 业务端点 → `ps -o lstart` 对比源文件 mtime → 进程外最小复现。
  本次网络(8ms DNS)、httpx、代码版本全正常，锁定「进程内连接池坏状态」。
- **`/tmp/mc.log` 是 append 日志，tail 里的 traceback 可能是几小时前的旧崩溃**
  （如 `max_keepalive` 拼错、`_auto` UnboundLocalError），别当现行故障。用 `ls -lT` 看 mtime 判断。

根因：`mc_api.py` 的 `post()` 虽写了「连接失败→重建 client→重试一次」的自愈，但
`_reset_client()` **无锁**。前端 10s 轮询 + 多面板并发，多个协程同时失败时反复互相
`aclose()` 掉刚建好的 client → 请求始终拿到已关闭的池 → 持续 ConnectError，
且每次失败又触发新一轮重建，形成自激循环，只有重启进程才断。另外 `get()` 当时**完全没有自愈**。

修复（`backend/mc_api.py`）：
- `_reset_client(seen=None)` 加 `asyncio.Lock` + 代次判断：`if seen is not None and self.client is not seen: return`
  （别人刚换过就不再关）。调用方先取 `cli = self.client`，失败时 `await self._reset_client(cli)`。
- `get()` 补齐与 `post()` 相同的自愈（取到坏连接会抛，必须重建重试）。
- 补 `logger`（自挂 StreamHandler + propagate=False，因为 uvicorn `--log-level warning`
  不会带上本模块 logger），连接失败打 `repr(e)`，以后能直接看到底层异常。
- 顺带把 `new.cookies.set(k, v)` 补回 `domain=".qq.com"`。

重启后：`./server.sh start`，`restore()` 从 `/tmp/mc_session.json` 自动恢复登录
（session 文件是 9/9 写的仍然有效，**无需重新扫码**）。
验证：`/api/state` 三连 200 且返回 nick 赵逍遥；`/api/cards/themes`、`/api/exchange/peers`、
`/api/exchange/auto/status`、`/api/auto/status`、`/api/card/plan` 全 200。

教训：**任何「进程内缓存/连接池」的自愈逻辑都必须加锁 + 代次校验**，
否则并发下自愈反而变成自激故障源；这类问题重启即恢复，容易被误判成「网络抖动」。

两处都错：① 未设置被认为「不能换」（实际是不限制）；② 非商店套（纸寿千年 1798，
不可购买）也被要求同套。

实测数据佐证：`纸寿千年(tid=1798)` 面额 82/287/373/796 → **无可购买套卡标记**；
`叹为观止(tid=1548)` 面额含 10 → 可购买。全局可购买套卡 487/1681 套。

### 修复（规则统一，避免再次漂移）
1. **`buyable_themes()` 上移到 `card_query.py`**（`@lru_cache(maxsize=1)`，返回 frozenset）。
   原因：`auto_exchange.py` 已 import `exchange`，exchange 不能反向 import（循环依赖）。
   两条链路现在共用同一份判据。
2. **`exchange._hit_from_box`** 改为：
   ```python
   exch_list = [int(x) for x in (p.get("exch") or []) if x]
   srcs = [... if s["price"] == pr
           and not (exch_set and s["theme_id"] in buyable and s["theme_id"] not in exch_set)]
   ```
   即 **exch 为空（未设置）→ 不限制**；下架/绝版套不受限；商店可买套才要求主题在 exch 里。
   同时新增 `want_themes: [{tid,name}]` 结构化字段（原来只有首个 `want_theme_id`）。
3. **`auto_exchange._pick_pay`** 同步加上「`exch_set` 非空才校验」的前置条件。
4. **前端 `app.js`**：判定完全交给后端的 `h.srcs`，删掉 `wantOk = !!h.want_theme_id` 这个
   错误的门槛；文案改为「对方想收：X」/「对方不限想收套 · 同面值即可换」/「他想要的套：
   不限（任何套卡均可）」；缺货时给出准确原因（面值不符 or 受想收限制）；顶部规则说明同步改写。

### 扫描慢（真因 + 唯一的提速手段）
读他人主页约 **15 次/10s 窗口**后开始 -3001，故串行 0.7s/人 ≈ 1.43 人/秒，**已经贴着限流上限**

### 教训
同一套业务规则出现在两条链路（手动/自动）时，**必须抽到公共模块只写一份**；
否则纠错只改一条，另一条会静默地继续用错规则 —— 这次就是自动换卡改了、手动没改。

## 20:0x 修「加载我的卡显示不出全部卡」（前端版本 → 20260910n）
- 现象：自动换卡面板点「加载我的卡」，列出的卡远少于自己实际拥有的卡。
- 排查证据链（不靠猜）：
  1. `/api/state` 解析完整：物理卡 161 张、唯一种类 142 种、全部带 price；原始 XML 核验
     各容器 `<card>` 元素与 `cur/max` 吻合（空槽 id=0 会被跳过），**服务端没漏卡**。
  2. jsdom 用真实 state 复现：输入框全空 → 142 行（全量）；**只要面值框有值 → 静默过滤**
     （面值 82 → 4 行、311 → 6 行、606 → 8 行）。
  3. 根因：`exLoadPayCards` 的面值取自 `#ex-autoex-price`，为空还会**回落到上方手动换卡面板的
     `#ex-price`** —— 用户搜纸寿千年时在那里填过 82，于是付出卡列表只剩 4 种，看着像卡没加载全。
- 修法（`frontend/app.js` + `index.html`）：
  - 过滤只认本行新增的 `#ex-pay-price`，**不再跨面板继承**；默认空 = 显示全部。
  - 汇总行 `#ex-pay-sum` 永远写明「已载入 N 张 / M 种（换卡箱 x + 保险箱 y）」+ 过滤状态，
    过滤时给「显示全部」按钮/链接，**不再静默过滤**。
  - 勾选状态独立存 `exPaySel: Set`（不再从 DOM 读），切面值/重加载不丢；`exPaySelected()` 改为读该 Set。
  - 列表容器限高 220px 可滚动 + 空白态提示文案。
- 测试 `/tmp/mc_pay_test.mjs`（jsdom + 真实 state）13/13；回归 mc_exchange_test 7/7、mc_pai_test 5/5。
- jsdom 坑：`initExchangeOnce()` 不调用则换卡页按钮未绑定；脚本级 `let exPayCache` 不能用
  `win.exPayCache=` 赋值（那是 window 属性，改不到词法绑定），要 `win.eval("exPayCache = ...")`。
