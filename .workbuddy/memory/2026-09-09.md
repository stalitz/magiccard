## 偷炉（slottype=steal）取卡——最终结论（已实测）
- **机制（用户澄清）**：炉位带 `slottype="steal"` 是**偷炉**——用好友空炉炼**自己的**卡。好友发现可收走（=偷失败）；好友不管则卡能收到**自己**卡箱。所以取卡按钮必须保留，不能隐藏。
- **关键判据（用户 2026-09-09 纠正）**：偷炉卡「能被看到=还能取」；若被好友收走会直接消失看不见。所以 slot6 仍可见即代表能取，之前 -32001 是参数错不是被收走。
- **取卡失败真正根因（实测纠正）**：普通端点 `card_stove_refinedcard_get`（slottype=1）对偷炉**永远** -32001，无论 slottype/opuin 怎么组合都失败——此端点不适用于偷炉。
  - 正确端点：**`card_stove_stealcard_get` + `opuin=<好友uin>`**（缺 opuin/带自己 uin 均失败，返回 -1002/-32001）。普通炉仍用 `card_stove_refinedcard_get`。
  - 实测：对 slot6（隋书 25510，好友 983688972）调 `card_stove_stealcard_get` 带 `opuin=983688972` → `code=0` 成功，炉位清空、卡入自己卡箱。**已用实验验证，非推断。**
- **代码改动**：
  - `mc_api.py`：新增 `get_steal_card(slotid, opuin)` 调 `card_stove_stealcard_get`（已 import `EP_STEAL_GET`）；`get_refined_card` docstring 改为"仅普通炉"。
  - `main.py` `/api/refine/get`：读 state 判该 slot——若 `slottype=="steal"` 或 `opuin!=自己uin` → 调 `get_steal_card`（带好友 opuin），否则 `get_refined_card`。
  - 前端无需改：偷炉炉位本就显示「可取卡（偷炉）」+ 取卡按钮，调 `/api/refine/get?slotid=X`，后端自动分流。
- **已验证**：后端重启后 `/api/me` 正常、空炉位6返回「没有已炼好的卡」、包导入 OK（get_steal_card 存在、EP_STEAL_GET 已导入）。偷炉取卡完整链路已闭合（实验已把 slot6 隋书收进卡箱）。
- 教训回扣：「别凭单点逻辑下结论」——我先误以为 -32001=被好友收走，用户点出"可见即能取"，遂用参数矩阵+换端点实验定位到 `card_stove_stealcard_get`，而非假设 slottype。

## 发行/下架能否从 card_lib.json 区分——结论反转
- 用户贴出两张截图要求分析现有数据能否区分"发行/下架"。**之前我把截图 tab 搞反了**——高亮 tab 实际是「发行套卡 419/419」，不是下架；所以截图里的卡是"发行"正例，不是下架。
- 两个开源项目（sxyy/magicCard + dwandw/mfkp）的源码都指向同一个过滤字段：**`theme_card_list` 的 `theme_type` 字段**（card ids 数组后第一个字段，对应 `card_lib.json` 的 `idx12`）。`card_info_v3.js` 字段注释明确：card ids 后依次是 `theme_type, version, time, offtime, flash_src_tid`。
- **mfkp** `js/page/base.js:17`：`checkJbCard(themeId) = (mapTheme[themeId][12] & 0x01)`，bit0=1 表示**绝版/下架**。
- **sxyy** `commonlib/carddatabase.py:105`：`get_grounding_card_list()` 用 `WHERE cardtheme.type=0 OR type=5` 取"未下架卡片以及非活动卡"；`isOffCard()` 查 theme type，非 0/5 即下架。
- 截图里 67 个"发行"套卡的 `theme_type` 分布：{0:33, 5:30, 1:4}。
  - type=0：全部 `offtime(idx15)=0`，未下架。
  - type=5：30 个，其中 27 个 `offtime=0`（未下架），3 个 `offtime>0`（军训记/飘香粽子/愚你同乐，是限时节日套卡但仍在发行 tab）。
  - type=1：4 个，全部 `offtime>0`（梦色蝴蝶兰/情溢中秋/酷爽果乐/甜蜜Dell灵越），说明 type=1 是已下架/限时套卡。
- 因此当前游戏数据里：商店可购买/未下架 ≈ `theme_type==0` 或 `theme_type==5` 且 `offtime==0`；`theme_type==1` 为已下架。`theme_type` 是本地数据里的上下架过滤参数（不是服务端实时过滤）。
- 验证 caveat：`card_market_npc_buy` 买卡接口当前 POST 返回 `-33002 系统繁忙`，未能在当前账号上完成 type=5 vs type=1 的真实购买对照实验，所以"可购买"规则主要依据两个开源项目源码 + 字段分布证据。`offtime` 是下架时间戳（idx15），未来可作为更直接的下架判断（offtime>0 且 offtime<now）。
- 教训：先从源码/已有实现定位过滤参数，而不是自己瞎猜字段——两个开源项目早就写明了 `theme_type` 和 `offtime`。

## 炼卡经济模型 v3：用户给定硬约束后的重算（收益可重复领 + 3炉位+2排队+1偷位）
- 用户给的硬参数：**3 炉位同时炼 + 2 排队位；偷位只能炼产物面值 40 的卡（第2偷位需VIP，不算）；
  每次合成全套都能再得一次套卡钱（奖励可重复领）；成本只有商店买卡钱 + 炼卡时间**。
- **底层基础卡 99.9% 是面值 10 的卡**（全发行套展开共 99261 张面值10，仅 100 张是 48/49 面值
  —— 来自美丽女人/梦幻童年这两套）。→ 成本结构极简：每轮就是买 N 张面值 10 的卡。
- **1★ 套只有 2 层配方**：七夕情人节/储存介质 = 6×(30→40,1h) + 1×(120→150,4h)，总炉时 10h、关键路径 5h；
  哏儿都味道 = 9×(30→40,1h)+1×(120→150,4h)，13h/5h。→ **86~90% 的配方产物是 40 面值，偷位可全包**，
  主炉 3 个只需处理 1 条 120→150(4h)。偷位成为瓶颈：单轮墙钟 ≈ 6h（七夕），不是 h/3=3.3h。
- 盈亏平衡单价 = Prize/底层卡张数（只算 Prize，卡被集卡册消耗不计面值增值）：
  七夕情人节 588/23=25.6、美丽女人 1238/23=53.8、叹为观止 6888/198=34.8、杏林春满 3666/116=31.6、
  望闻问切 1888/78=24.2、储存介质 588/27=21.8。
- 正收益套数敏感度（发行 402 套有配方）：单价10→57套 / 单价20→11套 / 单价50→仅2套 / 单价100→0套。
  → **商店卡价是生死线**。单价10最优仍是七夕(107/h)>储存介质(95/h)>哏儿都味道(62/h)；单价20则七夕38/h>美丽女人24/h。
- 待用户确认：①商店买面值10的卡单价 ②每日购买上限 ③偷位是否真能连续占用（好友空炉可得性）。

## 炼卡经济模型 v4（终版）：商店只卖面值10卡/20金币，偷位为全局瓶颈
- 用户确认硬参数：商店**只卖面值10的卡、20金币/张**；收益=套卡奖励(可重复领)；卖卡不划算。
- **硬约束修正**：21 套发行套的底层卡含非10面值(买不到)→ 不可重复刷，必须剔除。
  含：美丽女人/梦幻童年(底层49面值×3)、普天同庆(262)、孝道/孝心/春夏/秋冬(224)、手工织锦(48×8)等。
  剩余可用 399 套。→ 之前把美丽女人列为优选是错的，它根本无法持续刷。
- **偷位是全局瓶颈**：所有发行套都需要偷位（1★ 套结构统一 = 6×(30→40,1h)+1×(120→150,4h)，偷位占60%），
  **不存在 sh=0 的套**，故主炉闲置无法用其他套填补（七夕单刷主炉闲置 78%）。
- 每偷位小时奖励排序（免费卡场景）：七夕/储存介质 98 > 杏林春满 91.7 > 望闻问切 78.7 > 叹为观止 65。
- **双套 LP 最优（3主炉+1偷位满载，全量 399² 枚举）**：
  - 买卡场景(20金/张)：七夕情人节+杏林春满 = **28.9/h → 694/天**（七夕0.064轮/h + 杏林0.015轮/h，
    买卡支出 1565/天，毛利 2258/天）。单刷最优 叹为观止 26.8/h。
  - 免费卡场景(卡靠抽/偷/换/变)：**单刷七夕或储存介质 = 98/h → 2352/天**（双套反而降至94.1，因抢偷位）。
  - 七夕 vs 储存介质：结构完全相同(588奖励/6h偷位/4h主炉)，但七夕只需23张卡 vs 27张 → 买卡场景七夕净128/轮 vs 48/轮。
- **卖卡不划算的推断（已答用户）**：买20金币/张，集套回收 25.6金币/张(七夕588/23)；若卖卡价≥20则可无限套利，
  游戏不会这样设计 → 卖价必<20(很可能=面值10或更低)，卖即亏。集套是唯一正向路径。
- 买卡场景利润率仅 30%（2258毛-1565成本），卡成本吃掉 70% 收益 → **能否靠抽/偷/换/变拿到面值10卡是收益 4.6 倍的关键**。

## 炼卡经济模型 v6（推翻 v4/v5，两个硬 bug）—— 新建 backend/economy.py
用户新确认参数：①卡面额=卖价（面值10卖10金，买20卖10必亏，卖卡无套利）②10面值卡**无限买、只看钱**
③偷位**不限次数**、1小时/次、1★卡偷1次出40面值卡。
- **BUG1 配方去重（我错）**：素材在炼卡时被**消耗**，同一张 40 卡若既是套内卡又是 150 的素材必须炼 2 次。
  v5 用 set 去重 → 七夕偷位时少算一半（3h vs 实际 6h）。修法：MRP 物料展开（demand 按配方倍数累加），
  按配方树深度降序处理。七夕验证：底卡 23 张 = 6张40×3底卡(18) + 套内5张底 = 23 ✓
- **BUG2 偷位定位（我错）**："偷位只能炼40"是**偷位的能力上限**，不是"40只能偷位炼"——**主炉也能炼 40**。
  正确资源模型：4 个并行位（3主炉+1偷位）；产物40的配方 4 位都能做，产物≠40 只能主炉。
  约束：Σx·h_oth ≤ 3 且 Σx·(h40+h_oth) ≤ 4。v4 因误判偷位独占 40，把产能低估 2.4 倍。
- **v6 结论（发行套 399 套可持续刷，买卡场景仅 9 套正收益）**：
  - 最优 = **单刷七夕情人节(1★)**：奖励588、底卡23、成本460、净利128/轮；h40=6h、hoth=4h；
    节拍 = min(3/4, 4/10)=0.4轮/h → **2.5h/轮** → **51.2 金币/h → 1229/天**（毛利5645、买卡4416、利润率21.8%）。
  - 免费卡场景（底卡靠抽/偷/换/变）：七夕或储存介质 **235/h → 5645/天**（2.5h 节拍）。
  - 备选：储存介质(1★)同结构588奖励但底卡27 → 净48/轮、19.2/h；杏林春满22.6/h；望闻问切20.8/h。
  - LP 枚举全部单套+双套极点，单刷七夕即全局最优（双套反而降，因抢工时）。
- **排程**：单轮最快 5h（1h 炼3张40 → 4h 炼150，另3张40 并行在 2h 内完成）；稳态 2.5h/轮需 2 轮流水线并行
  （卡箱需同时容纳约 50 张卡）。启动本金 460 金/轮，2 轮并行约 920 金周转。
- 399 套中仅 9 套正收益的根因：底卡 20 金/张，而套卡回收均值 10.5 金/张 → 卡价吃掉 78%。
- 脚本：`backend/economy.py`（analyze 做 MRP 展开、lp_best 做 2 约束 LP 极点枚举、collect_only 找纯收集套），
  可直接 `python backend/economy.py`。

## 各星级结果 + "为什么别人几万几万涨"（用户质疑日收益只有1229太少）

  因底卡张数涨得比奖励快。2★最优望闻问切 20.8/h(499/天)、过年回家 10.8/h；3★最优研精覃思(下架)42.2/h(1013/天)、

  梦幻童年(49×3)、手工织锦(48×8)。399+3=402 与"402套有配方"吻合。

  4 位 ×24h = 96 工时 → **5645/天（底卡免费）/ 1229/天（买卡）**。反推：日入1万需 7.1 个并行炉位、
  日入3万需 21.3 个（当前只有 4 个）→ 靠炼卡不可能几万。
- **真正的金币大头 = 纯收集套（关键发现）**：全库 **1029 套的卡全部"无配方"**（多为 type=5 下架），
