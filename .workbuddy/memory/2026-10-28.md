## 1) 「DP 是投炉顺序不是时刻表」→ 逐 op 日志挖出两个执行层实现缺陷

用户定调链：「各环节的衔接有问题，不是算法的问题，修吧」。

**新增排查工具**：`MC_DBG_OP=1` 逐 op 执行日志（`self._oplog`，默认关）。
记录 `(tick, op#, cid, 动作, miss_buy, feeders)`，动作含 开炉/偷炉/无炉位/
未到期跳过/应急买/等料打不开。**这个日志是这轮唯一的突破口** —— 没有它只能瞎猜。

**bug1（真 bug，已修）：`_not_due` 分支误用 `protected` 锁料**
未到期的 op 也把箱内喂料加入 `protected` → cursor 附近 7 个 op 互相锁死 →
能发的 op 一个也发不出 → **每 tick 空转**。
铁证：AD 逐 op 日志 38 行 / ORDER **5066 行**，全部是「未到期跳过」且 `miss_buy=()`（料齐）。
`protected` 的语义是「**已到期**但投不了的 op 锁自己的料」，未到期的 op 没有锁料权利
（前序料由 `early_ok` 的 reserved 段按 start 覆盖 cursor..idx 来预留，够用）。
修后：4★ −2.06 → **−3.41h**，买卡 193→186。

**修2：早发只给「长链」开口子**
判据用骨架自己算的 `cp`（向上关键路径），阈值取 refine op 的 cp 中位数。
提前生产要付库存代价（中间层躺箱 + 占炉占箱）：长链早开直接缩短完工，短链早发纯堆库存。
修后：3★ +1.35 → **−0.02h**。

**证伪并删除：「早发留给期头动作留 1 个炉」**
（`main_free-used_main < 2` 就不早发）。理由看似充分（早发占满炉 → 管仲到期无炉 →
重解把它 7.050→9.050 往后排），但实测 4★ 78.06→82.10h **且 err=30**、1★ +1.00h err=6。

## 排队位定论：任何场景都不该用（13:50，全量实测）

## 人在环：人手动往排队位投卡，计划还对不对？（14:25 实测）

真实使用里人不会一直盯，看到空卡位就手投两张 —— 这是**外部干预**，不走
`_main_cap`。探针 `/tmp/humanq.py`：在指定 tick 往 actions 注入 refine（绕过引擎
自我约束），分「投计划内」与「投计划外」两模式。3★ tid=59，基线 45.86h / refined 43。

| 干预 | 累计投卡 | 时长 | Δ | refined |
|---|---|---|---|---|
| 无（基线） | 0 | 45.86h | — | 43 |
| 一次投 2 张·计划内 | 2 | 46.27h | +0.41 | 43 |
| 一次投 2 张·计划外 | 2 | 47.11h | +1.25 | 45 |
| 三次投·计划内 | 11 | 47.91h | **+2.05** | 43 |
| 三次投·计划外 | 10 | 61.25h | **+15.39** | **53** |

→ **计划会自愈，但不会替你撤销错误决定**：
- 每次重解都从「箱 + 炉」重算净需求，人投的卡计入 `pending` → 需求自动减少/转移，
  最终都能收敛完成、**没有重复炼同一张**（planned 的 refined 与基线完全相同 = 43）。
- 代价按「投对了没」分化：投计划内 ≈ **+0.19h/张**（等于提前开工，几乎免费）；
  投计划外 ≈ **+1.5h/张**（基线单张炼卡成本才 1.07h → 白炼还倒赔），且多占箱位。
- 纠正**不是立刻的**：`state_sig`（含炉内容）只在「空计划」时触发重解；计划非空时
  靠 `discrepancy > max(12, ops//4)` 累积、`exhausted`、轮次变化。实测单次干预多
  22~39 次重解。

**结论：排队位唯一的正确用法是「人按计划投」，不是「人自由投」。** 要做的是让人
一眼知道管线里下一步该投哪张（现在 `dp_stats_last` 只透传 plan_ops/cursor 等数字，
不含具体卡），而不是让引擎自己去预排（已证伪，见上一条）。

## ★ 修正上一条：投「计划内」也会慢，因为没到 `start` 就是提前开工

5. **正反馈**：囤得越多 → `max(持有)` 越大 → sets 越大；真机保险箱 168 格能继续装，于是囤到 13 张才停。

### ★ 用户纠正：封顶要用「空位」不是「总容量」（提交 01b3c65）
用户原话：「给套数加箱位硬顶：sets ≤ 换卡箱容量 ÷ 这套卡张数, 你这是什么破修法, 理论上,
如果换卡箱空位 9, 收卡时如果没有获取到奖励卡, 那可以炼无限套, 不是 1 套」。

我的 e82d6f3 两处错：
① 用 `change_cur`（总容量）而不是**空位** `cur - used` —— 箱里已有存货时高估并行度；
② 把「本轮同时铺开几套」当成「总共能炼几套」。一套的卡是**滚动消耗**的，只要空位够一套
流转就能一直炼（`max_rounds=0` = 无限套）；该限的只是**在途并行度**——6 套同时铺开才会
「三张 40 面全在等」把箱塞死。

改成 `sets ≤ max(1, (cur - used) // len(plan.ids))`，`_box_used` 每 tick 从 `len(st["change"])` 取。
空位充足自动放开（178 空位 18 → 2 套），箱紧收回 1 套。
