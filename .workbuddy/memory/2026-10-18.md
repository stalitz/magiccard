### 自动炼卡-变卡目标「只变同一张」根因与修复（20261018 晚）
- **用户报告**：2星自动炼卡时变卡环节又只变一种卡（七雄Q传 孙膑被连变 7 张堆保险箱，刚炼150面卡消耗1张→箱里剩6）。此前 2026-10-03 已优化过（held_c 升序），用户质疑"为什么还只变同一张"。
- **根因（卡箱证据闭环）**：`pick_change_target` 主排序 held_c(持有最少优先) 被**每 tick 炼卡吃掉40面素材**→ 下一 tick held_c 又归0 → 主排序打平 → 二级落「缺口最大」→ 缺口最大的那张(孙膑,缺口7)永远胜出。即 2026-10-03 只改了主排序，没解决"held_c 每 tick 被重置"这个前提。
- **修复**：二级排序加 `rot`(本会话该卡被变次数) 升序——held_c 相同时优先选被变最少的卡，多张不同40面卡轮流被变出。实现：`pick_change_target` 增 `rot` 参数；引擎加 `self._change_rot` 计数；`_drain_box_gift`/`_gift_drain` 变卡成功 `+=changed`；`_pick_change_dst` 透传。`rot=None`(手动变卡)退化为原缺口优先不影响。
- **实测(unit)**：七雄Q传 孙膑缺口7 旧逻辑必选；rot=7 后改选王翦(缺口5)；连续10次分布 `孙膑→王翦→吕不韦→李牧→蒙恬→…` 均匀轮转。py_compile 通过，`./server.sh stop&&start` 重启生效，已 commit（backend/auto_refine.py 单文件）。
- 注意：**重启会清空运行中的自动炼卡内存进程**，修复后需从界面重新点「开始」。

### 自动炼卡-变卡「轮转」不是好算法 → 改为「分布变卡」（20261018 深夜，回应 20261018晚那轮）
- **用户尖锐批评**：轮转（rot）本质是好算法吗？40面卡本就是给更高面额(150)当素材的，应该**先看合成路径、把需要的40面都变齐，再去炼150**；实测 20 张礼物卡≈变出10张却只堆成一种40面卡、其余种类仍从底卡炼 → 卡炉还在炼一堆40面额，"优先变卡变了个寂寞"。正在跑的正是 tid=290 七雄Q传(2星)，它有 **5 种不同40面卡**（蒙恬/吕不韦/孙膑/王翦/李牧，空库存需求 孙膑×7/吕不韦×5/王翦×5/蒙恬×3/李牧×3）。
- **根因（实锤）**：`drain_box_gift_cards`/`drain_gift_box` 旧版拿**单个 dstid** 把礼物卡全变进同一张40面卡（变出一张即停 / 连变也只盯一个目标）；而 `_face40_credit` 里那段"按缺口轮着发、让不同种类都变到"的逻辑，在 `box_gift_change` 打开时因礼物卡已被即时变掉、`_gift_cards_left` 返回0 而**永远返回空**——纯死代码。于是礼物卡全堆成一种，其余种类只能 `net_plan` 从底卡炼。
- **修复（合成路径驱动的分布变卡）**：
  - 新增引擎方法 `_change_specs(stock,pending)`：对队列各套调 `net_plan(credit=空)`，把"本该从底卡炼的40面 runs"按需求量降序列出（= 合成路径真正缺的40面种类与张数），交给变卡环节**分散**变出，直接替代"买10面卡+炼40面"那一步，卡炉腾出来炼150。
  - `gift.py` 加 `_pick_dst`（按剩余需求轮转选下一个缺失种类）；`drain_box_gift_cards`/`drain_gift_box` 新增 `dst_specs=[(dst,need),...]` 参数：有 specs 时轮流分散到各缺失种类、需求填满即停（不浪费礼物卡），无 specs(手动单目标)保留旧"变出一张即停"行为。
  - `_drain_box_gift`/`_gift_drain` 改用 `_change_specs` 生成分布目标；`box_gift_last/gift_last` 增 `per_dst` 用于 status 显示。
- **验证**：① 编译通过；② 脚本确认多套卡有2~7种40面卡（婚礼6/开心畅享7/七雄Q传5），且 `_change_specs` 等价逻辑对七雄Q传返回 孙膑×7/吕不韦×5/王翦×5/蒙恬×3/李牧×3；③ 单测 `_pick_dst` 轮转：15次变卡恰好产出 7×101/5×100/3×99，三类全覆盖、按量分配、不再只盯一张。`prices HTTP 200`、引擎重启后照常跑。`./server.sh stop&&start` 重载生效。
- 结论：轮转那轮(20261018晚)是治标（只在单目标内换张），本轮是治本（多目标按量分布）；rot 仅作相等缺口下的兜底 tie-break，不再是主机制。

## 自动炼卡调度重构：即时拉动 / 不囤卡（20261018深夜，用户定调）
- **根因（代码实证）**：`_refine_all` 每 tick 把整套 `net_plan` 的 `runs`（含全部40面+上层）全排进炉、缺料当场买底卡现炼。变卡每 tick 只供约10张40面(按 `_change_specs` 分布)，但一套(七雄Q传 tid=290)要23张40面 → 其余13张全被算进 `runs` 现造 → 表现为"炼一堆40面额"+底卡囤箱。用户判"轮转不是好算法、变了个寂寞"正确。
- **用户原则**：变卡填40层；卡炉 freed 后优先拿箱里已有的卡**合成**上层(150/80…)，**绝不现买现造缺的40面**；3个炉在同时炼，理想是箱里零囤卡。只有4层2星都炼不明白，怀疑高星逻辑。
- **改法**：`tick` 预测 `self._gift_will_supply`（箱里有礼物套48面卡 或 礼物箱≥upper → True）；`_refine_all` 拆两阶段：① 阶段一 `allow_buy=False` 只合成(素材全在箱才投，天然只投150+/不投40)；② 阶段二仅当 `not _gift_will_supply` 才 `allow_buy=True` 现造40面(变卡耗尽才兜底，防卡死)。`_prepare_turn` 加 `allow_buy` 开关；抽 `_submit_one` 共用主炉/偷炉投炉动作；偷炉同受 `manu_allowed` 约束。
- **验证**：离线单测 `_chk_gate.py`（已删）断言全过：A 上层素材在箱→合成 OK 且0买卡；B1 40面底卡不在箱+`allow_buy=False`→None 且0买卡（门槛挡现造）；B2 +`allow_buy=True`→OK 且发3次 EP_BUY（现造路径活）。编译通过、`prices 200`、`./server.sh stop&&start` 重载生效。
- 注意：重启清空内存进程，界面需重新点"开始"用新版；高星卡同理适用（两阶段只认"素材是否在箱"，与星数无关）。

## 自动炼卡·"在途40收齐再合成"闸门（20261018深夜续，用户追问"人觉得高效是否真高效"）
- **新增 `_imminent_synthesis`**：某上层目标 T 的全部 40 面配料都已「在箱或在炉(在途)」→ 判定 imminent=True → `_refine_all` 阶段二(现造40)整体关闭，空炉等那几张在途卡收好即合成 150，不去现造第4张40。直接解决用户"收1张后空炉去炼别的40、收齐发现囤了1张"的观察（`_chk_imm.py` 三用例全过：配料齐→True、缺1→False、全空→False 不误关 bootstrap）。
- **逻辑结论（用户要求用逻辑判断而非盲从"人觉得好"）**：40面炼制1h且3炉并行(产能3张/h) ≫ 150/高层合成4h串行(需求0.75张/h)，故**瓶颈在高层合成、不在40面产能**。结果：①"等3张收齐再合成"对**总完成时间几乎无影响**(稳态速率由4h合成决定)，人的"越快炼高层越省时间"感知其实是"优先合成而非现造40"的phase-1已完成，等待本身不提速；②真正收益是**箱位卫生**(少囤40)与**防卡箱满死锁**(箱满时囤卡会阻塞流水线，那时不等才真掉速)。③本闸门是"按需求节流40产能"的压力阀：imminent 时40已够→停产；40真短缺(无imminent)→复产，**不会饿死合成**。编译通过、`./server.sh stop&&start` 重载、prices 200。重启清空内存进程，界面重点"开始"。
