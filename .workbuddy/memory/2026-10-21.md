## 「追加队列」（多套并行）机制梳理 + 空间可行性实测（只读，未改码）
- **是什么**：`POST /api/auto/queue/add?tid=<主题ID>` = 追加**另一个主题**（不是同一套的第 2 份；同一套多份走 `surplus_sets`）。必须引擎 running 时才能加。
- **四层编排**（`auto_refine._refine_all`）：
  1. 轮转起点 `order = queue[_rr % len:] + queue[:_rr % len]`（`_rr` 每 tick +1，防第一套独吞炉位）
  2. **按炉次交错**：`while any(buckets): for tid in order: seq.append((tid, buckets[tid].pop(0)))` —— 若一套把炉次全提交完再轮下一套，多套并行会**退化成单套串行**（2026-09-17 离线验证抓到）
  3. 套内排序 `_sort_time_aware`：就绪优先 → 占炉时长降序 → 深度降序 → 落后度优先
  4. 两阶段投料：阶段一仅从箱存合成上层卡（allow_buy=False）→ 阶段二才现造 40 面底卡（仅当变卡不供 40 面时）
- **套数 `_calc_sets`**：1星 = `max(囤的40面卡数)`（以炉位数+1 封顶，用 max 不用 min）；其他星 = 剩余未收集 qq秀数（至少 1）
- **出队**：达 `max_rounds` 移出队列；上交后**立刻**重读库存续炼（不等 45s）
- ★ **空间机制（回答用户"能追加几套/空间够不够"）**：
  - 真实容量：换卡箱 cur=18（已放 10，剩 8）；保险箱 cur=168（已放 160，**只剩 8**）；炉位 3 个。
  - **腾位策略 `_make_room`（用户定调"优先移保险箱"）**：① 换卡箱里「不属于任何在炼套卡」的高面值杂卡 → **移入保险箱（无损）**；② 10 面值底卡垫后才卖（炼卡素材，用多少买多少）；③ **在炼套卡自己的卡受保护、不动**；④ 保险箱也满 → 卖杂卡保底。
  - **保护范围**：`keep_ids = ∪ 各在炼主题的所有卡` → **队列里每套主题的全部卡都被保护**（不能移/不能卖/不能当素材）。实测追加 N 套 → 受保护卡种类 9/25/47/69/97（1~5套），**在换卡箱里的受保护卡=0**（当前换卡箱 10 张全是无关杂卡 → 10 张都可腾）。
  - **风险点**：保险箱只剩 8 格而换卡箱剩 8 格 → 移保险箱的余量已经很紧；**保险箱满后只能卖杂卡**，而杂卡数量随"在炼主题保护卡变多"而变少 → **理论上追加越多越容易卡死**。当前 5 套候选主题在换卡箱里 0 张受保护 → 眼下安全。
  - 各候选主题占位：1652(1星) 40面3种/9卡；1776(2星) 6种/16卡；1752(3星) 5种/22卡；1810(3星) 5种/22卡；1548(4星) 4种/28卡。

## ★ 干预场景：花钱收5星顶层 → 引擎必须反转优先级（2026-10-21 傍晚）
- 场景：JIT调度运行中（4星正在炼溢出填充），用户突然花钱收了5星顶层卡（顶层瞬间完成，跳过100h燃烧）。此时4星未上交、卡箱不够5星低层卡。
- 核心：JIT调度的最大假设"顶层还要烧100h、有slack"被人为捷径直接打破 → 引擎绝不能继续跑陈旧的deferral计划，必须每tick从实时状态重算。
- 正确响应（4步）：
  1. 侦测：重读发现5星顶层卡已在箱 → "顶层剩余时间"≈0 → JIT截止线塌缩为"现在"（deferral条件 top_remaining>low_chain+buffer 翻FALSE → 5星低层立即变强制）。
  2. 反转优先级：5星翻P0（关键路径、零slack），4星→defer，停开新4星炉次。
  3. 给5星低层腾箱：把4星在箱的暂存料移保险箱（无损）——要求放宽keep_ids对MOVE的保护（protected=不被卖，但高优先级套饿箱时允许移保险箱）；保险箱也满→退化卖10面底卡/告警。
  4. 不浪费在途4星：已在烧的4星炉让其烧完（中止白烧源卡），但不再喂；烧完收进已腾出的箱/保险箱。
- 诚实失败态：箱+保险箱都放不下5星低层料 → 顶层已买但整套交不了 → 引擎必须明确告警"顶层已收但箱满无法炼低层，需手动腾位"，不静默空转。
- 设计原则：优先级可反转、基于实时状态每tick重算、绝不缓存"顶层还在烧"的ETA；protected=不卖但高优先级饿箱时可移保险箱。当前引擎（无JIT gate）对此无感知，只会轮转交错继续——正是待实现的A轻量闸门要补的。


## ★ 腾箱机制补充：向上合（3合1）优先于挪保险箱（2026-10-21 傍晚，承接上条）
- 用户补充场景：4星在炼、箱满，5星顶层已收需低层卡。除了挪4星料去保险箱，更优的是把4星暂存料向上炼（3合1）——上层卡把低层卡消耗完，卡数净减2/每组合，不新增卡，箱自然空出够放5星。
- 修订后的腾箱优先级（箱危机、5星P0时）：① 压实4星（向上合3合1，净减卡数，不新增）——主；② 没凑齐3张无法合时，才挪保险箱——次；③ 箱+保险箱都满，卖10面底卡/告警——兜底。
- 炉位争用解：压实与炼5星低层同为"腾箱/交5星"目标下动作，可共用炉；压实是临时借炉，腾出箱后让位5星低层。顺序铁律：先压实腾位、再买/炼5星低层（不能先买5星料——没位放）。
- 泛化原则：箱紧张时优先"减少卡数"的动作（向上合），而非"增加卡数"的动作（买料）。这是3合1固定树机制的天然红利。
- 当前引擎缺口：_make_room 只会挪/卖，不会主动向上合来腾位——是A轻量闸门要补的另一块。


## ★ 腾箱机制再补：级联合成（买最少卡触发多米诺清空）（2026-10-21 傍晚）
- 用户再补：箱紧时还可能补少量新卡腾4星箱——若4星合成路径每层都少1张（每级恰有2张），买最底层的1张就能一路合到上层，清空所有占位的4星卡。
- 威力：压实（3合1）要求有3张才能合，而每层少1根本凑不出3张→压实失效；但买1张底层→级联把所有占位4星卡清空，箱占用从N张骤降到1张顶层卡。这是压实解决不了的情形。
- 修订腾箱优先级（5星P0、箱危机）：① 级联解锁买（检测4星子树买最少张就能触发全合，优先买1张底层）→ 主；② 压实3合1 → 次；③ 挪保险箱 → 再次；④ 卖10面底卡/告警 → 兜底。
- 泛化：箱紧时最优动作常是买最少卡解锁级联，而非买一堆料；每张买入换来的腾位最大。买的通常是最底层10面卡（授权内、便宜），占位高值卡不被卖、只被合→无损，与用户不卖高值卡铁律一致。
- 当前引擎缺口：无任何级联检测/解锁买逻辑，_make_room 只挪/卖/（将来的）合。是A轻量闸门要补的又一环。


## ★ 腾箱终止条件：够位即转向5星（2026-10-21 傍晚）
- 用户补充：级联/压实腾箱只是手段，目的是给5星腾位。一旦卡箱空间够5星所需，就停止向上合4星、立刻转向炼5星（5星始终P0），不要过度压实4星。
- 即最小恢复即转向原则：每做一次腾箱动作后重算箱余位，余位>=5星所需即break腾箱、切5星精炼。避免把炉次浪费在过度压实4星上（5星顶层已收=零slack，炉次应优先5星）。
- 5星所需空间 = 其低层精炼期间峰值并发占位数（保守估）。
- 当前引擎缺口：无任何阈值转向逻辑；A闸门要把恢复动作门控于5星所需阈值、够位即Pivot写进去。


## ★ 队列准入控制（实时可行子集，承接JIT讨论，2026-10-21 晚）
- 用户举具体例：队列选3套 60/40/20 张、卡箱80。原则：
  - 炼60(=dominant P0)时，60+40=100>80 超容 → 40 不能一直炼，到一定程度必须停（会挤占60收卡）；
  - 60+20=80 刚好 → 20 可在**不影响60收卡时间**下一直炼（溢出填充）；
  - 即"可行活动子集"= 选队列里使 `dominant_peak + admitted_peak <= 卡箱容量` 的子集，其余 defer。
- 关键：准入是**实时、每tick重算**的（卡箱因合成消耗/收卡动态空出→可能重新准入被defer的套；反之箱满→踢出）。
- 与前面JIT/反转/腾箱是一体：准入决定"哪些套同时在场"，JIT/反转/腾箱决定"在场套之间如何分炉分箱"。引擎当前完全无此机制（_refine_all 把队列所有套无脑交错），是A轻量闸门的核心缺口。


## ★ 用户结论确认：当前多套队列引擎在紧箱场景下不安全（2026-10-21 晚）
- 用户原话："你之前上了多套可以队列的引擎，其实是不能用的，是吧"。
- 诚实结论：引擎在**机械层**能用（能 add 多主题、轮转交错提交、并行炼），但**完全无**准入控制/JIT/反转/腾箱(级联压实)。
- 后果：① 紧箱(两/多套峰值和>容量)时，轮转交错会把各套碎片都搬进箱、keep_ids 又保护它们→`_make_room` 腾不出→落进"囤两套哪个都完不成"死局；② 混合优先级时不会保护 dominant 的收卡时间。
- 即：引擎只适用于"每套都宽裕塞得下、不在乎精确时序"的舒适区；一旦涉及"容量/时序耦合"（用户觉得复杂的地方），它假装复杂不存在→做错。这是 5 层 A 轻量闸门要补的本质缺口。

- 关键测量(sched_cmp，五档星)：|星|引擎→贪心|贪心→DP|DP占缺口| 1星 0.01h/1.00h/99% · 2星 -5.99h(引擎赢)/6.00h · 3星 10.70h/2.00h/16% · 4星 8.89h/82.17h/90% · 5星 34.01h/16.00h/32%。→ "卡快收了等它当素材可能快1小时"正是贪心看不到的critical-path/slack，4星贪心→DP差82h实测量化。
- 架构教训：这问题本质是**在线RCPSP**(资源受限项目调度：3合1前驱+可再生资源炉/箱+人随时干预)。正确形态=滚动重规划(每决策点从当前态重算)，不是一次性ILP。轻量DP(sched_dp已支持init_stock/running/free，5星0.1s/1星0.02s)只在该用时用：多套争箱+高星；简单情形走贪心快路径。**既不"永远贪心"(用户批评)也不"热路径搬重OR"(用户警告)**。
- 代码教训：`_refine_all` 是 god-function(提交+腾箱+偷炉+队列全混)。应拆 planner(调度/何时炼/放谁) + executor(纯API)。
