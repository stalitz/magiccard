**症状**：腾讯 skey 过期后，界面仍显示「已登录」，实际取不到数据（/api/state 返回 -1001 请重新登陆）；

- `frontend/app.js`：
  - 新增 `forceLogin(reason)`：清标记、停轮询、showLogin + loadQr(reason)。
  - `loadState` 收到 `need_login / code=-1001 /「重新登陆」` → 调 `forceLogin`。
  - `loadQr(reason)` 接受 reason（避免内部固定文案覆盖过期提示）。
  - 启动 IIFE：me 未登录/过期直接弹扫码（无需手动点退出）。

**验证**：后端 `/api/me` 真实探测生效；jsdom 回归 `/tmp/mc_login_test.mjs` 7/7
（启动过期→弹码 / 运行中过期→loadState 自动切回扫码）。旧回归 mc_pai_test、mc_exchange_test、mc_pay_test 未受影响。

**教训**：「内存登录标志」≠「真实可用会话」，凡涉及登录态判断的接口都应做一次轻量真实探测，

## 二维码接口 500 / 后台进程代理过期致 httpx ConnectError（2026-09-11 复盘二）
**症状**：重启服务后，登录页二维码显示不出来；`/api/login/qr?force=1` 返回 500，body「Internal Server Error」，
`/tmp/mc.log` 报 `httpx.ConnectError: All connection attempts failed`。

**定位**
- curl `https://ssl.ptlogin2.qq.com/ptqrshow` 直连返回 403（网络通），但后端 httpx 报 ConnectError → 非网络层问题。
- 诊断脚本实测：同一机器 `httpx.AsyncClient()`（默认 trust_env=True，走环境代理）与 `trust_env=False`（直连）**均返回 403 成功**；
  环境变量含 `HTTPS_PROXY=http://127.0.0.1:xxxx`。说明**后台 server 进程继承的代理端口已失效**，httpx 走死端口 → ConnectError，
  而 curl 走当前有效代理故能通，造成「curl 通、service 挂」的假象。

**改动**
- `backend/auth_qr.py`：`QRLogin.client` 加 `trust_env=False`（腾讯登录服务国内直连可达，不读环境代理）。
- `backend/mc_api.py`：主连接池 client 初始化（`__init__`）与 `_reset_client` 重建两处均加 `trust_env=False`（同源根治，避免游戏接口也因代理过期断连）。
- 另：`backend/main.py` 的 `_require_login` 补 `need_login:true`，让前端区分「服务端无登录态（应弹码）」与「连接错误（仅重试不弹码）」，不与 conn_error 的 `code:-1` 撞码。
- 前端版本仍为 **20260911b**（仅后端逻辑改动，前端 JS 未变）。

**验证**：`/api/login/qr?force=1` 重启后返回 `{"qr":"data:image/png;base64,iVBOR..."}` 有效 PNG，二维码图恢复。

**教训（重要）**：凡后端 httpx 访问腾讯系（国内直连可达）的 client，**必须显式 `trust_env=False` 直连**，
不要依赖环境代理——后台进程继承的 `HTTPS_PROXY` 指向的本地端口常随代理软件重启而变，一旦失效即间歇性 ConnectError（且 curl 能通掩盖之）。

## 二维码「假已扫描」根因（2026-09-11 复盘三）
**症状**：未扫码却显示已扫描，前两次加固未根除。
**真因**：腾讯 ptlogin2 的轮询接口，在「未扫描」与「已扫描」时，ptuiCB 第一个返回码都是 66，二者只能靠第 5 字段提示文案区分——「二维码未失效」=未扫，「二维码已扫描,请确认」=已扫。原代码只抓第一个数字 66，故未扫描被判成已扫描。
**改动**：`backend/auth_qr.py` 的 `poll()` 改为取全部字段，仅当文案含「已扫描/确认」才判 scanned，其余（含 66+未失效）一律 waiting；code 0 登录成功、67 失效。
**验证**：未扫码连续 poll 现稳定返回 `status=waiting`（修复前为 scanned）。
**教训**：解析第三方登录态接口必须核对真实返回语义，不能想当然套返回码；QQ ptlogin2 不能用 66 直接判已扫。

## 扫码后显示「已失效」但手机已登录（2026-09-11 复盘四）
**症状**：用户扫完二维码、手机侧显示已登录，但网页却显示「二维码已失效」（前端仅当 poll 返回 status=expired 才显示此文案 → 后端 `poll()` 回了 67）。
**真因（两类，均导致后端轮询的 qrsig 与用户实际扫的码不一致，或被短暂确认态 0 漏掉）**
1. **刷新覆盖 qrsig**：`/api/login/qr` 在 `force=1` 时无条件 `get_qr()` 重新生成 qrsig，而前端 `loadQr` 永远带 `?force=1`。
   一旦用户在「已扫描/待确认」途中点「刷新二维码」（或两次 loadQr 并发、响应乱序），后端 `_qr.qrsig` 被换成新值，
   前端却显示旧码 → 用户扫旧码（手机登录成功），后端轮询新 qrsig → 67。原 100s 复用缓存形同虚设。
2. **漏掉确认态 0**：QQ 确认态 `0` 极短暂，2.5s 轮询若恰好错过，直接落到消费后的 67。

**改动**
- `backend/auth_qr.py`：`QRLogin` 增 `used` 标记（确认成功/失效后置 True，取新码时清 False）；`poll()` 在 ok/expired 置 `used=True`，并加诊断日志（每次非等待态记 qrsig 尾 8 位 + code + msg）。
- `backend/main.py` `login_qr`：`force=1` 仅在「无缓存 / 已过期 / 当前码已 used(消费或失效)」时才重新生成；**未消费的码即使 force 也复用同一张**，根治刷新覆盖待确认扫码。
- `frontend/app.js`：轮询提速（2.5s→1.5s），扫到 `scanned` 后加速到 700ms 抓确认态 0；`expired` 若发生在 `sawScanned` 之后改为「登录确认中…」并短暂重试（上限 4 次），不再直接判死成「已失效」；超时再提示刷新重扫。版本 20260911b → **20260911c**。
**验证**：`py_compile` 通过；重启后 `/api/login/qr?force=1` 正常返回 PNG，未扫码连续 poll 稳定 waiting。
**教训**：扫码登录的「取码」与「轮询」必须共用同一稳定 qrsig；`force=1` 不应无条件换码，否则会覆盖正在进行的扫码。`force=1` 的正确语义是「丢弃已死的码」，不是「每次都换新」。

## 扫码后「已失效 + [object PointerEvent]」根因（2026-09-11 复盘五）
**症状（用户三连发）**
1. 一扫就显示「二维码已失效」，但手机 QQ 点登录直接成功。
2. 登录成功界面不变（始终停在扫码页）。
3. 点「刷新二维码」没刷出新码，状态文字直接显示 `[object PointerEvent]`。

**真因**
- **(3) `[object PointerEvent]`**：`app.js` 的 `qr-refresh.onclick = loadQr;` 把按钮点击事件当 `reason` 传入 `loadQr`，
  `setQrStatus(reason, "warn")` 内部 `el.textContent = reason` 把 PointerEvent toString 成 `[object PointerEvent]` 显示出来。
- **(1)(2) 一扫就失效的更隐蔽根因**（上一轮 `login_qr` 复用策略仍不够）——
  复用条件是 `(not valid) or (force and _qr.used)`：当**上一会话**手机已确认了 qrsig（腾讯侧标记 consumed）、
  而**我们漏掉了 code 0 确认窗口**（极短）导致 `_qr.used` 仍是 False，新页面 `loadQr?force=1` 命中 `_qr.used=False` 走「复用缓存」，
  把一张**已死的码**又返给前端。用户扫它必然 67（`sawScanned=False` → 直接「已失效」），而手机是上一次确认时已成功。
  这正是「现象是已失效、推演是复用通常正确」的反例——必须读真实状态，不要让现象迁就结论。

**改动**
- `backend/main.py` `login_qr`：
  - 加 `import asyncio` + `_qr_gen_lock = asyncio.Lock()` 单飞，避免并发 `get_qr` 产生两个不同 qrsig 导致「显示的码 ≠ poll 用的码」。
  - 简化 `need_new = (not valid) or bool(force)`：**`force=1` 始终重新生成**（去掉 `_qr.used` 短路），彻底杜绝跨页面复用已死码。
  - 响应里加 `qrsig_tail`，前端可与 poll 响应对照排错。
  - `login_poll` 非 ok 分支也带 `qrsig_tail`。
- `frontend/app.js`：
  - `$("qr-refresh").onclick = () => loadQr("refresh")` —— 显式传字符串，不再把 event 漏进去。
  - `loadQr(reason)` 防御：非字符串 reason 收敛成可读文案（"refresh"/"auto-refresh"），彻底消除 `[object PointerEvent]` 出现路径。
  - `pollOnce` 收到 `expired` 先 `/api/me` 探测一次：若 `logged_in`（漏掉的 0 窗口但 cookie 实际到了）→ 直接 `showDash`，不再误报失败。
  - 探测后仍未登录 → **自动 `loadQr("auto-refresh")` 拉新码**（用户无需再点刷新），且把状态改成「正在自动拉取新码…」。
  - `log` 加 `qrsig_tail` 输出，便于对照排错。
- 前端版本 20260911c → **20260911d**。

**验证**（py_compile + 重启 + curl）：
- 三次连点 `?force=1` 分别得到不同 qrsig_tail（`f53f9294`→`406b5e28`→`157aab93`），确认 `force=1` 始终再生。
- poll 返回的 `qrsig_tail` 与最近一次 qr 一致（`157aab93`），前后端用的同一张码。
- 未扫码 poll 稳定 waiting。

**教训**
- 按钮 `onclick = func` 会把 `PointerEvent` 漏给 `func`，要么包成 `() => func()`，要么在 `func` 内部对非字符串参数做防御。
- 「状态复用」必须配「状态死亡信号」双向闭环：跨会话/跨页面时，被外部（手机侧）消费的信号你这边永远收不到，
  所以**任何「可能已死」的码都不能再复用**，宁可多生成一张。
- `force=1` 的语义要统一：要么永远再生（本次方案），要么精确描述「仅当 used 时再生」并加跨进程重置；混用最容易出 bug。

## 自动换码顶掉用户正在扫的码（2026-09-11 复盘六）
**症状**：扫完二维码页面**自动刷新**了二维码，随后手机提示「扫的二维码失效」、无法登录。
**真因**：上一轮（复盘五）我加的「expired → 自动 `loadQr("auto-refresh")`」改过头了。
重新取码会向腾讯申请**新 qrsig**，而 qrsig 是**按会话（cookie）绑定**的——同一会话下取新码会使旧码立即失效。
用户扫的正是那张旧码，于是手机端确认时提示失效，登录彻底失败（比之前更糟）。
**改动**
- `frontend/app.js` `pollOnce` 的 `expired` 分支：**移除所有自动重新取码**，改为本地提示「请点『刷新二维码』」，
  把换码决定权交回用户；保留「先 `/api/me` 探测、若其实已登录则直接进主面板」的兜底。
  已扫描后的 67 仍保留少量重试（覆盖 0 略滞后到达），超过上限也只提示手动刷新、不自动换码。
- 轮询提速：`POLL_NORMAL` 1500→**1200**、`POLL_FAST` 700→**500**，提高抓住短暂确认态 0 的概率。
- 前端版本 20260911d → **20260911e**。
**验证**：新增 jsdom 回归 `/tmp/mc_qr_test.mjs` **10/10**（刷新按钮文案干净且真的换码 / expired 不自动换码 /
已登录兜底进主面板 / 传对象给 loadQr 也不出 `[object ...]`）；旧 `/tmp/mc_login_test.mjs` exit=0 未受影响。
**教训（重要）**：**任何「自动重新取码」都可能顶掉用户正在扫的码**——qrsig 是会话绑定的，取新即废旧。
扫码流程里「取新码」只能由用户显式触发（点刷新），绝不能在轮询/超时逻辑里自动做。
自动化的边界：能自动「探测状态」，不能自动「换凭据」。

## 【根因定案】扫完码显示"已失效"、手机却登录成功（2026-09-11 复盘七）
**症状**：扫完二维码 → 页面显示"二维码已失效"；手机端显示登录成功；永远进不去主界面。用户："以前都是可以的"。
**真因**：`backend/auth_qr.py` `poll()` 里 `if code == "67": return {"status": "expired"}` **排在文案判断之前**，
把"扫完待确认"短路成了"失效"。
**腾讯 ptuiCB 实测语义（此前注释一直是错的，本次校正）**：
- 未扫描 → `code=66` +「二维码未失效。」
- **已扫描待确认 → `code=67` +「二维码已扫描，请在手机上确认。」** ← 67 不是失效！
- 已确认 → `code=0` +「登录成功！」
链路死锁：67 被判 expired → 前端 `clearInterval` 停轮询 → 手机确认后腾讯返回的 `0` **永远收不到** → 卡在登录页。
**改动**
- `poll()` 改为**文案优先**：先排否定词（"未失效/未扫描/未过期"→waiting，注意**「未失效」本身含"失效"二字**，
  必须先判否则等待扫码会被误判失效）→ "已扫描/已扫码/确认"→scanned → "失效/过期/取消/无效"→expired → 兜底 waiting。
  **彻底删除按 code 判断失效的逻辑**；文案识别不出时降级 waiting（继续轮询），保证后续 `0` 仍能被收到。
- **硬兜底**：`poll()` 里只要 cookie jar 出现 `skey` 即视为登录成功（不看返回码/文案）——skey 是登录完成的唯一铁证。
  配套：`get_qr()` 开头 `self.client.cookies.clear()`（新码=新会话），否则兜底会把上一轮的旧 skey 误判成本次登录。
- 前端 `pollOnce` 的 `expired` 分支：**降速继续轮询**（新增 `POLL_SLOW=3000`），绝不停死、绝不自动换码。
- 版本 20260911e → **20260911f**。
**踩到的两个「静默坑」**
1. **logger 名**：只有 `mc.api` 配了 handler 且 `propagate=False`，root 无 handler →
   用 `logging.getLogger("mc.qr")` 的日志被**静默丢弃**（上一轮"加了日志却什么都没有"的原因）。
   必须挂到 `mc.api` 层级下（现用 `mc.api.qr`）。另：Formatter 硬编码前缀 `mc.api:`，grep 时别按 logger 名搜，按消息内容搜。
2. **文案否定词**：`"失效" in "二维码未失效。"` 为真 → 必须先判"未失效"。
**验证**：新增 `/tmp/mc_poll_parse_test.py` **9/9**（含 67→scanned、67+失效文案→expired、未失效否定词、
skey 兜底触发、仅 qrsig 不误判）；`/tmp/mc_qr_test.mjs` 前端回归 **10/10**；端到端未扫码 poll 稳定 `waiting` 且日志可见。
**教训**：**能证明"登录成功"的只有凭据本身（skey），不要用返回码/文案当唯一判据**——
第三方状态机的码位语义不可信（同一码复用在不同阶段），拿不到权威文档时就按"最终凭据 + 文案兜底 + 不停轮询"三层设计。

## 换卡面板「加载我的卡」整块不可见（2026-09-11 复盘八）
**症状**：换卡面板里「付出卡（可选）/ 加载我的卡」那一整行连同卡片列表**完全看不到**，

用 headless Chrome + CDP 实测元素**真实高度**：`/tmp/mc_cdp_probe.mjs`
（`--remote-debugging-port` + Node 内置 WebSocket，`Runtime.evaluate` 量 `getBoundingClientRect` 与 `scrollHeight`，再 `Page.captureScreenshot`）。
**实测铁证**：`#ex-autoex` → `height=9px / scrollHeight=385px / clipped=true`（内容 385px 被压成 9px）；

—— flex column 的子项默认 `flex-shrink:1`，容器高度不足时子项被压缩；
`.cb-box{overflow:hidden}`（为圆角）再把挤出部分整块裁掉。
今早新增的 `#ex-pay-sum` + `#ex-pay-list`（max-height:220px）把 `#ex-autoex` 内容撑到 385px，正好触发。
**修复**：`frontend/index.html` CSS 加 `#ex-body > *{flex-shrink:0}`（滚动交给 `.lst` 自带的 `overflow-y:auto`）。
**验证**：CDP 复测 `#ex-autoex` → `height=387px / flexShrink=0 / clipped=false`；截图确认「付出卡（可选）｜加载我的卡｜面值」整行可见；
`/tmp/mc_pay_test.mjs` 13/13 未受影响。仅 `#ex-body` 是 flex 版 `.lst`，其余 4 处 `.lst` 为普通 block，无同类隐患。
**教训**：`flex column` 容器 + 子项 `overflow:hidden` 是脆弱组合——子项内容一涨就会被压缩+裁切。
**视觉问题要用真实浏览器量高度定位，别靠读代码推演**（jsdom 无布局引擎，量不出这类问题）。

## 已实现：手动换卡「指定卡（可多选）」v20260911g

用户确认的需求：「腾讯没有按卡搜人的接口，所以是从指定套卡的人中筛选出有指定卡的人，可以指定多个卡」。

**后端**（`exchange.py` / `main.py`）
- 新增纯函数 `normalize_picked(idx, theme_id, card_id, card_ids) -> set[int]`：去重、丢非法值、**剔除不属于该套的卡**
  （卡 id 全局唯一，用户串套时若不剔除 → 一个都扫不到且界面看不出原因）。
- `_hit_from_box` 的 `card_id` 参数改为 `card_ids` 集合：`if card_ids and cid not in card_ids: continue`（空集 = 不筛）。
- `scan_peers` 新增 `card_ids: list | None`，兼容旧的 `card_id`；返回体新增 `card_ids` / `card_names` 回显。
- `/api/exchange/scan` 透传 `card_ids`（与既有的自动换卡 `card_ids` 语义对齐）。

**前端**（`app.js` / `index.html`）
- 选定目标套后自动拉 `/api/cards/theme/{tid}`，渲染「指定卡」候选 chip（可点选/取消、卡名过滤、一键清空）；
  换套时**强制重置**已选卡（否则串套）。
- `doScan` 请求体带 `card_ids: [...exState.pickCards]`；结果文案显示「指定「卡名…」」，扫不到时提示可清空指定扩大范围。
- 事件绑定做判空保护：浏览器若缓存旧 `index.html`（DOM 无新元素），不能让整个换卡面板绑定中断。

**验证**
- 后端单测 `/tmp/mc_cardids_test.py` **13/13**（归一化 7 + 命中筛选 6）；端到端 `card_ids:[5427,5426]` → 回显 `card_names:["风土人情","大美新疆"]`。

- CDP 真实浏览器复测：候选 46 张全部渲染、点 3 张 → `nActive=3`、文案「已指定 3 张：…」。

**教训 1（重要，连中两次）**：**同一文件的多处 Edit 不能并行发送** —— 会互相覆盖，且每次单独都返回 "Successfully edited"。
本轮 `exchange.py` 出现「签名改了、函数体没改、还在用未定义的 `picked`」，`app.js` 出现「doScan 改好了、事件绑定整段丢失」。
**正确做法：同文件多处改动一律串行，改完立刻 `grep` 复核关键符号**（py_compile 只查语法，查不出变量丢失/逻辑半改）。

**教训 2（CSS 老坑复发）**：`.lib{display:flex;flex-direction:column}` 下的**任何新增直接子项都要显式 `flex:0 0 auto`**，
否则内容一多就被压扁。本轮 `#ex-card-cands`（46 张卡）被压到 44px（内容 93px），只能滚一行半。
已加 `#ex-theme-cands,#ex-card-wrap,#ex-card-cands{flex:0 0 auto}`。这与昨/今两次 `#ex-body` 裁切、`#ex-autoex` 压成 9px 是**同一个根因**——
**再往 `#pane-exchange` 里加任何内容块，先想 flex-shrink**。
