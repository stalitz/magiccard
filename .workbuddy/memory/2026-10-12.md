## 自动炼卡：上交选 qq秀 + 流水线 两连修（backend/auto_refine.py）

用户反馈：自动炼卡"快齐后空炉"、自动上交选了**已收集**的 qq秀、且"等一套齐后才炼新的一套"，与既定"多套流水线、不空炉、上交选未收集 qq秀"逻辑不符。

### 根因① 上交永远选已收集 qq秀
- `card_collection_add` 的 `giftid` 用的是 `t[9]` 首项（`plan.giftid`），但 `t[9]` 的 giftid（如 614）与 `card_collection_get` 的 `qqshow_str`（已收集实例 id，如 608624）是**不同命名空间**——靠 `gift_list` 把 giftid 翻成实例 id 比对才知哪个已收集。
- 旧逻辑永远传 614，而 614 已收集（用户 qqshow_str=608624,608629）→ 反复上交同一个已收集的。
- 修复：`tick()` 上交前遍历 `plan.gifts`(t[9] 全量)，用 `_gift_info_map()`(gift_list) 翻实例 id，挑第一个不在 `self._tick_collected`(qqshow_str) 里的；成功上交后把实例 id 写回缓存（20s 窗口内下一轮不重复选）。实测 203 现选 612(吴韵汉风2，未收集) 而非 614。

### 根因② 空炉 / 等一套齐后才炼新的一套
- `tick()` step3 上交后 `if progressed: return steps` —— 上交那一轮直接 return，干等 45s 下一 tick 才续炼 → 炉子空 45s、表现为"等一套齐后才炼新的一套"。
- 非 1 星 `_calc_sets` sets=0 永远返回 1 → 每次只排 1 套，不并行。
- 修复：① 上交后 **同 tick 重读库存 + 继续 `_refine_all`**（流水线续炼，炉位不空）；② `_calc_sets` 非 1 星 sets=0 改按「未收集 qq秀数」定套数（`min(uncollected, free_stove+1)`，至少 1），多套并行铺炉。

### 验证
- 离线脚本确认 203 挑未收集逻辑正确（614/613 已收集→选 612）。
- 重启 backend + 启动 203：`running=True`、`sets_now={'吴韵汉风':2}`（2 套并行）、炼卡/买卡/偷炉持续、无 Traceback、errors=1（仅取卡时箱满的良性提示）。
- 新增只读探针 `tools/peek_qqshow.py`（比对 t[9] vs qqshow_str 命名空间，调试用）。

### 注意
- 改 backend 必须 `server.sh stop && start` 真重载；`_collected_shows` 每 tick 读一次 `card_collection_get`（只读、廉价），缓存 20s。
- 1 星逻辑不变（仍按囤卡算多套）；本次只动非 1 星的"按未收集 qq秀定套数"。

## 偷炉选友：统一为「等级高优先」（exp 降序）2026-10-12

用户纠正：偷炉应该去**等级高（活跃几率大）**的好友，别老去不玩的人。

### 数据实锤（拉 card_user_list 原始响应）
- `<user>` 标签属性只有 `uin/nick/exp/vip_*/turn`，**无 level 字段**；顺序 = **uin 升序**，与等级/活跃度无关（推翻旧注释"顺序=游戏界面顺序"）。
- 但有 `exp`（经验值 = 等级代理）。
- 游戏内好友界面（用户看到的下拉）是**等级序**（另一视图）；`card_user_list` 与它不是同一排序。

### 不一致点（真 bug）
- **前端偷炉「常去好友」下拉**（`app.js:2788 loadStealFriends`）早已按 `exp` 降序排（高等级在前）——用户看到的就是这个。
- **后端引擎** `_pick_steal_friend` 之前用 `card_user_list[-12:]`（uin 序末尾），跟等级/活跃度无关 → 引擎实际去偷的人和用户在下拉里看到的高等级好友**不是同一批**，造成"去不玩的人家"的错觉。

### 修复（backend/auto_refine.py）
- `_load_friends`：解析 `<user uin exp>`，额外建 `self._friends_by_exp`（按 exp 降序）。
- `_pick_steal_friend`：从 `friends_by_exp[:steal_search_depth]`（等级最高前 12）扫，第一个有空主炉就借；`preferred` 锁定、`busy`(挂着我未取回的卡)/`fail`(失败缓存) 排除保留。
- 离线验证：exp 降序 top12 = 3344577(1.7亿)/1317585016(1.3亿)/191901398(1.3亿)/… 真正的高等级；旧逻辑偷的 3934268479(exp=149万) 在新排序里排第 28，**不再被优先**。
- 重启 backend 生效，`running=True`、无 Traceback。

### 结论
现在**前后端一致 = 等级高优先**；偷炉自动挑高等级（活跃）好友，没空炉才顺延。用户若想锁定某人，仍可在下拉选「常去好友」走 `preferred` 分支。
