## 1. 问题定位与核心矛盾

本系统是一个**离散时间、多资源约束、在线干扰下的组合调度问题**，归类为**资源受限项目调度（RCPSP）的在线变体**，并在其基础上叠加一个游戏特有维度：**卡箱空间是可经 3→1 合成回收的资源**（不是纯消耗约束）。

**核心矛盾：**

| 目标 | 约束 |
|---|---|
| 全局最优（最小总完成时间） | 离线 DP 仅 0.1s（5★）/ 0.02s（1★），但那是"纯可行表"；168s 是证书开销，线上从不需要 |
| 实时响应（人随时干预） | 排产表随时过期，不能预计算 |
| 高频决策 | 每个 tick（45s）必须出结果 |

**结论（已实测验证，非假设）：不存在"全局最优 + 预计算排产表"的单一方案。正确形态是单一滚动重规划器——每个决策点从当前真实状态重算，不维护离线表。**

> ★ 实测依据（2026-10-20）：扰动（炉被占 / 中间卡被买掉）下，**离线排产表与滚动重规划的 makespan 完全相同**（1★ sets=2 扰动后都是 14.00h），而滚动重规划总耗时仅 0.3s，且免除了"表 ↔ 实时状态同步"那套复杂度。→ **离线排产表已放弃**，不要重建。

## 3. 分层架构

```
人干预（不可预测、随时发生）
        │
        ▼
┌──────────────────────────────────────────────┐
│  TickLoop（编排，每 45s 或干预事件触发）        │
│  刷新 WorldState → Planner.decide() → Executor │
│  → 回读 → 循环。人干预天然被"每 tick 重读"吸收  │
└──────────────────────────────────────────────┘

  WorldState（读状态层）    Model（静态模型层）
        │                        │
        └──────────┬─────────────┘
                   ▼
        ┌──────────────────────────────────────┐
        │  Planner.decide()  —— 纯决策，无副作用 │
        │   ① PriorityResolver   反转优先级（先定 P0）│
        │   ② AdmissionControl   准入控制（预留 P0 峰值）│
        │   ③ ScheduleStrategy   JIT 延迟门       │
        │   ④ BoxCompaction      级联>压实>挪>卖10>告警 + 阈值转向 │
        │   ⑤ SolverDispatch     DP 按需 / 贪心   │
        └──────────────────────────────────────┘
                   │  产出 Plan（契约）
                   ▼
        ┌──────────────────────────────────────┐
        │  Executor —— 纯 API，无决策逻辑         │
        │  逐 action 翻译为请求，每步后重读槽位    │
        └──────────────────────────────────────┘

  StealAudit（跨层横切）：借炼记账 + 白炼感知 + 换友
```

### 3.1 WorldState（读状态层）
- 职责：每个决策 tick 调 `parse_full()` + 炉位端点，快照当前真实状态。
- 输出结构：`{change, store, safe, furnaces:{main_free, steal_free, in_use[], pending[]}, capacity:{change_cur, store_cur}}`
- 关键：**动态可用容量实时算出，不缓存**（卡箱因合成消耗 / 收卡随时变）。

### 3.2 Model（静态模型层）
- `ThemePlan(tid)`：`comp` 合成树、`_card_secs` 各层炉时、`peak = len(ids)`（峰值箱占用保守上界）、`priority`（星档 / 用户指定 / `top_bought` 标志）。
- `economy`：炉时模型（已有）。
- **仅在队列变更时重建，不进热循环**（避免重复算合成树）。

### 3.3 Planner.decide()（决策层 · 纯函数）
- 签名：`decide(ws: WorldState, models: dict, queue: list[int]) -> Plan`
- 5 步顺序流水线（见 §4），互相独立、可单测。**顺序铁律：先定 P0（PriorityResolver）再准入（AdmissionControl）**——P0 是谁决定了要预留谁的峰值箱位，顺序反了会让"事后翻 P0 的套"进不了场。
- **原则**：纯函数、无网络、无副作用；所有"下一步炼什么 / 队列放谁 / 等不等素材"都由它算。

### 3.4 Plan（契约层）
- 纯数据结构，Planner 与 Executor 之间唯一耦合点。
- `Plan = list[Action]`，`Action = {action, target_card, set_id, priority, depends_on, admission}`。

### 3.5 Executor（执行层 · 纯 API）
- 签名：`execute(plan: Plan) -> ExecResult`
- 逐 action 翻译为请求（交炉 / 买 / 卖 / 移 / 合成），**每步后重读槽位**（防 `-311 卡牌有变化`）。
- **无决策逻辑**：不知道为何这么做，只照做。
- **★ 卡炉不空职责**：在 Planner 准入许可的套内，把 **3 主炉 + 1 偷炉 + 2 排队位全部喂满**（有就绪炉次就提交下一张），直接服务用户"卡炉一直不空"目标。排队位由服务端自动管理，Executor 只需"有空位就填"，不关心排队概念本身。

### 3.6 StealAudit（横切）
- 借炼时记 `(friend, target, 期望收取时刻)`；下 tick 发现卡消失 → 计入白炼、换"不常收卡"好友。
- 详见 §6。

## 4. Planner 五步流水线（核心领域逻辑）

> 这 5 步是**一个决策的不同侧面**，合并在 `decide()` 内顺序调用，不拆成 5 个类（避免 bureaucracy）。
> **顺序铁律**：① 先 `PriorityResolver` 定 P0 → ② 再 `AdmissionControl` 按 P0 峰值预留 → ③ JIT → ④ 腾箱 → ⑤ 派发。

### Step 1 — PriorityResolver（反转优先级，先定 P0）
**解决：人突然花钱收顶层 → 要保它**
```
P0 = 队列里必须按时交的套（最大 / 最高星 / 用户指定 / 最近截止）
若某套 top 卡已在箱（top_bought / 已收顶层 / 已变顶层）：
    → 该套翻 P0，slack = 0（覆盖上面的默认 P0 选择）
    → 其余套标记 defer（停开新炉次），给 P0 让位
```
- 这是 JIT 门"延迟"条件的反向触发：顶层剩余时间 ≈ 0 → 延迟条件翻 FALSE → 喂料立即变强制。
- **必须先于准入**：P0 是谁决定了要预留谁的峰值箱位；若某套准入时被 defer 了，之后才因 `top_bought` 翻 P0，就进不了场。

### Step 2 — AdmissionControl（准入控制）
**解决：囤两套哪个都完不成（死局）**
```
余量 = capacity.change_cur - P0.peak            # 峰值用保守上界（套总张数，见下注）
active, deferred = [P0], []
for s in 队列其余套（按优先级 / 队列序）:
    if 余量 - s.peak >= 0:
        active.append(s); 余量 -= s.peak
    else:
        s → deferred（不启动、不喂料）
```
- **峰值上界 `peak`**：默认 `= len(ids)`（套总张数，绝对安全）；可收紧为"合成树最宽层的卡数"（更贴合实际并发占用，减少误挡）。两者都是保守估计，宁严勿松。
- **动态、每 tick 重算**：箱因合成 / 收卡空出 → 被 defer 的套可能重新准入；反之箱满 → 踢出。
- **★ 时间感知（瞬态占用，2026-10-22 用户细化）**：`peak=len(ids)` 是箱占用**静态快照上界**，但被准入的卡若在窗口内会被炼掉，则净占用远低于快照。例如第 2 套取 150 需带 3×40，炼 150 时这 3 张 40 被消耗、150 再向上合 → 实际只暂占箱、窗口内净清。判定必须从「静态峰值快照」升级为「**含消耗时间轴的动态峰值**」：
  - 若长时套（如 540 顶层）剩余炉时内、被取卡能被消耗掉且不挤占当前套交付所需箱位 → 「取出能正好消耗掉」就准入；
  - 若取出后箱位被长期占住、或挤占当前套完成所需空间 → 「先不取」。
  - 输入全可推算：**炼卡时间 + 卡炉状态 + 卡箱状态**。等价把 AdmissionControl 从 `dominant_peak + admitted_peak <= cap`（静态）升级为「峰值随消耗时间轴收敛」的动态约束。
- **迟滞（hysteresis）**：准入后除非箱低于某阈值才踢，避免反复抖动（见 §7 风险 4）。

#### 准入决策算法（自推导，2026-10-22 由「时间感知」引子推得）
> 输入全部可推算：**炼卡时间(`_card_secs`/`economy`) + 卡炉状态(`free_main`/各炉 `endtime`) + 卡箱状态(`changebox`/`storebox` 占用, 含保险箱)**。无外部未知量。

**① 不可逾越的保留量 `reserve_S1`（"保证能上交整套"的硬约束）**
当前在炼套 S1 仍需占箱的 = 它**尚未入炉的剩余树节点数**（即完成 S1 必须再持有的卡）。任何 S2 的准入必须满足：
```
F >= reserve_S1 + transient_peak(S2)      # F = 当前可腾箱位(双箱合计)
```
`reserve_S1` 永不被 S2 吃掉 —— 这是死局与"交不了整套"的分界线。

**② `transient_peak(S)`：时间轴动态峰值（取代静态 `len(ids)`）**
对候选套 S 在 [now, now+t_feed] 窗口内、把它的下一批可执行动作（如取 150 需带 3×40）拉入箱，求箱占用随时间的最大值：
```
t_feed(S)   = 取/买 feeder 耗时 + 炼下一张产品炉时 + 该产品向上合炉时
transient_peak(S) = max_t∈[0,t_feed] box_occ(t)   # feeder 被消耗后即回落，故峰值出现在早期
```
例：S2 取 150 → 拉 3×40（box +3）→ 炼 150 吃掉 3×40 产出 1（box −2）→ 150 向上合（box −1）。`transient_peak=3`（非套总张数）。

**③ 触发时机（"先不取" vs "可取"的判据）**
```
remain_T = S1 顶层长卡剩余炉时
if  F >= reserve_S1 + transient_peak(S2):
    if  t_feed(S2) <= remain_T + slack:        # S2 的卡在 T 烧完前能被消耗掉
        准入 S2（取卡 / 启动其下一批炉次）
    else:
        "先不取" —— 等 remain_T 收敛到 < t_feed(S2) 再拉（S2 卡不会长期占箱）
else:
    defer S2（箱不够放瞬态峰）→ 但空炉仍由 JIT 门填短套
```

**④ 多候选：贪心按 `transient_peak` 升序填**
队列里多个可填套时，优先选 `transient_peak` 最小且 `t_feed` 能消耗掉的，最大化箱利用率且不挡 S1。

**⑤ 偷炉的角色（消耗 40 的额外通道）**
偷炉只收 40 面卡 → 是**额外消耗 40 的炉容**。S2 取 150 堆积的 3×40，可分流 1 张去主炉(炼150)、其余走偷炉炼掉，加速箱清空，缩短 `t_feed`、压低 `transient_peak` 持续时间。

**⑥ 边界 case（自推导，无需再问）**
- **case A 重囤 40 滞后**：若买/囤 40 耗时 > `remain_T`，则把 40 的购买推迟到 `remain_T` 足够小再拉，期间不占箱；只要 `F - 40_count >= reserve_S1` 即可先拉，否则等。
- **case B 箱连瞬态都放不下**：S2 整体 defer；空炉改填 S1 自身低层（若有）或更短第三套——即 JIT 溢出填充，绝不因 S2 卡住。
- **case C 顶层进入 JIT 喂料窗**（`remain_T <= feeder_chain + buffer`）：停止接纳任何新 S2 工作，所有炉/箱转向保 S1 完成（接 gate 5 阈值转向）。
- **case D 多套并发预留**：`reserve_S1` 只保"当前在炼那套"；已准入的 S2/S3 各自也有 `reserve`，形成 `reserve_S1 + Σtransient_peak(已准入) <= F` 的累积约束，超限即踢最末套（迟滞防抖）。
- **case E 保险箱/换卡箱双箱拆分**：`F` 是双箱可腾合计，但换卡箱硬 18、保险箱 ~200 各自有上限；Executor 落实际动作时须按单箱容量分配（活卡在换卡箱、囤货在保险箱），AdmissionControl 只看合计上界。
- **case F 人随时干预**：任何手动 add/remove 主题、手动买卡，下一 tick 重算即生效（滚动重规划），不缓存旧准入。

#### 时间轴动态峰值 · 覆盖场景全表（自推导）
> 静态 `peak=len(ids)` 只抓"某刻最多同时持多少张"。动态峰值的意义 = **箱占在窗口内会变化**，下列事件都会让"瞬态峰 ≠ 快照峰"。凡涉及窗口内箱占变化的，都必须进时间轴，不能看死一个数。

**Ⅰ. 占用下降事件（使瞬态峰 < 快照峰）**
| 场景 | 机制 | 对瞬态峰影响 | 示例 |
|---|---|---|---|
| 合成消耗 | 3合1 吃掉 feeder | feeder 入箱后随即被吃，峰早现早落 | 取 150 拉 3×40 → 炼掉 → 峰=3 非套总张数 |
| 整套上交清空 | delivery 一次性移除整套 | 整套管占瞬间归零 → 后续准入空间释放 | S1 顶层好+上交 → S1 全部占箱释放，S2 可放宽 |
| 压实 3→1 | 去重合成 3 张同卡→1 张 | 净腾 2 格 | 多余 10/40 面冗余卡压实 |
| 卖 10 面底卡腾箱 | 负占用（仅 10 面，铁律不卖高值） | 峰下行 | 箱危机卖多余底卡 |
| 挪保险箱 | 总量不变，但换卡箱 18 硬约束缓解 | 换卡箱峰降（总峰不变） | 囤货移保险箱，腾出换卡箱给活卡 |

**Ⅱ. 占用上升 / 滞留事件（使峰渐起或久滞）**
| 场景 | 机制 | 对瞬态峰影响 | 示例 |
|---|---|---|---|
| 分批买入/囤积 | 卡非 t=0 同时到，占用随买爬升 | 峰 = 最大同时持有，非瞬时 +N | 逐批买 40，边买边炼则峰低；买而不炼则峰滞留 |
| 炉位瓶颈滞留 | 拉了但 3 主炉满，卡箱里等 | 峰持续偏高直到炉空 | S1 长顶层占主炉，S2 feeder 拉入干等 |
| 偷炉约束 | 非 40 面不能进偷炉，只能等主炉 | 非 40 产品滞留更久 | S2 要炼 150(非40原料? 否)→ 40 可走偷炉，非40 不可 |
| 失败/白炼重买 | 变卡失败烧源、偷炉被收走白炼 → 重获 | 额外瞬态（重买重占） | 变卡失败烧 1 张 40 → 再买 1 张 → 峰再 +1 |

**Ⅲ. 需求突变事件（改变保留量 / 叠加需求）**
| 场景 | 机制 | 对约束影响 | 示例 |
|---|---|---|---|
| 花钱收顶层 | top 直接买 → 该套剩余树需求缩水 | `reserve_S1` 缩小 → 释放准入空间 | S1 买 540 顶层 → 不用再囤其下层 feeder 链 |
| 多套同层争抢 | 虽每套卡不共享，但同面额 feeder 同期都要 | 窗口内该面额总需求叠加 | S2、S3 同时需 40 → 40 总持=两者之和 |
| 人干预增减主题 | 下一 tick 重算 | 约束整体刷新 | 手动 add S3 / remove S2 |

**Ⅳ. 时间轴前瞻（window 本身）**
| 场景 | 机制 | 对准入决策 | 示例 |
|---|---|---|---|
| 前瞻交付事件 | 看 S1 即将上交 → 提前放宽 |  horizon 短→现在可多准入 | S1 剩 30min 上交 → 现在就拉 S2 不挡 |
| 长顶层窗口 | `remain_T` 大 → 只准入窗口内被消耗的 | horizon 长→只接能消化的 | 540 还有 9h → 只接 t_feed<9h 且不挡 S1 的 |

**Ⅴ. 容量边界 · 条件副作用与运算顺序（1 空位死锁，2026-10-22 用户补充）**
| 场景 | 机制 | 对瞬态峰影响 | 解法（自推导） |
|---|---|---|---|
| 取卡奖励副作用 | 取/收卡可能触发**卡奖励**（条件 +1 占） | 仅 1 空位时取卡可能爆仓 → 静态判定"取不了" | **运算顺序 + 分支**：先不买 10 面（保 1 空位）→ 先收/取最终卡 → 分支：得奖励=真不够位（须先腾 1 格：卖 10 面/挪箱，铁律不卖高值）→ 没奖励=取完再买 10 面，买完箱恰满直接上交 |

- **本质**：`take` 动作**非槽中性**——它带条件副作用（卡奖励概率 +1 占）。在容量边界（剩 1 格）盲目"取 + 买"会死锁；正确做法是把**确定性买卡推迟到条件性取卡结算之后**，再按实际结果分支。
- **规划器须建模**：`take` 的占用 = 确定 +1 + 条件 +1（奖励）；准入/序列安排须**先结算条件动作再排确定动作**，并对"奖励出现"分支预留腾箱动作（卖 10 面 / 挪保险箱），对"无奖励"分支走"取→买→满箱直交"快路径。

> 结论：AdmissionControl 必须把"窗口内箱占轨迹"算出来（合成/上交/买卖/挪箱/失败重买/人干预/**取卡奖励条件副作用**都会改轨迹），用轨迹最大值当峰，而非 `len(ids)` 死数。这就是"时间轴动态峰值"要覆盖的全部场景（Ⅰ~Ⅴ）。

### Step 3 — ScheduleStrategy（JIT 延迟门）
**解决：长时套溢出窗口浪费（空炉）**
```
对每张候选卡：
  if 候选 ∈ P0 喂料层 且 top_remaining > feeder_chain + buffer:
      → 延迟（让炉 / 箱给溢出套）
  elif top_remaining <= feeder_chain + buffer:
      → 强制 JIT 炼 P0 低层（倒推"最晚开炼时刻"，过了就强制，不再让位）
  else（候选是溢出套 / 已进入 JIT 窗口）:
      → 正常炼
```
- 参数：`_set_furnace_hours`（顶层总时，当前代码已定义但**未接入**）、`_card_secs`（单层炉时）、`buffer`（保守安全余量，需量化，见 §7 风险 3）。

### Step 4 — BoxCompaction（腾箱策略 + 阈值转向）
**解决：箱满腾不出；且腾箱是手段、给 P0 腾位是目的**
```
threshold = P0 所需峰值箱位
repeat:
    余位 = capacity.change_cur（重算）
    if 余位 >= threshold:
        break 腾箱 → 立刻转向 Step 5 / 炼 P0   # ★ 阈值转向：够位即停，不过度压实
    elif 4星子树买最少张能触发全合（每层少 1 → 买 1 底层 → 多米诺清空）:
        → 级联解锁买（买最底层 10 面卡，授权内、便宜）   # 主
    elif 有 3 张可向上合:
        → 压实 3→1                                    # 次
    elif 合不了:
        → 移保险箱（无损）                             # 再次
    elif 箱 + 保险箱都满:
        → 卖 10 面底卡 / 告警（兜底，绝不卖高值卡）       # 兜底
```
- **级联 > 压实 > 挪 > 卖10 > 告警** 是腾箱动作优先级；前两者直接**减少卡数**（最优选），后两者是搬家 / 止损。
- **阈值转向**：腾到够 P0 即停，P0（零 slack）炉次优先，不浪费在过度压实 4 星上。
- 与用户铁律一致：占位的 4 星高值卡**一张都不卖**，只被向上合成 / 移保险箱。

### Step 5 — SolverDispatch（DP 按需 vs 贪心）
**解决：卡快收了等不等当素材（贪心看不到 critical-path / slack）**
```
if 多套争箱 且 高星（3/4/5★ 这类 DP 占缺口显著）:
    → 调 sched_dp 滚动重规划（支持 init_stock / init_running / init_machine_free）
else:
    → 贪心快路径（LPT / HLF，微秒级）
```
- **实测依据**：4★ 贪心 → DP 差 **82.17h**（占缺口 90%），1★ 差 1.00h（占 99%）、3★ 差 2.00h（16%）、5★ 差 16.00h（32%）。→ DP 在 3/4/5★ 介入有净收益，1★ 不必。
- 单次成本（2026-10-24 修复后，`time_budget=2s` 截断值）：1★ 0.02s / 3★ 0.1s / 4★ 0.05s（913 节点，修复前 22s 只搜 15 节点）/ 5★ 0.1s，远小于 45s tick。根实例全星阶「DP 值 == 模拟 makespan」已由 `_verify_sched` 证明（求解器可信度前提）。
- **边界**：DP 求解器**只在 dispatch 内按需调用，绝不进 tick 热循环本体**；`sched_cmp` 的离线评测与线上零耦合。

## 5. 状态表示（聚合而非枚举）

```
✗ 错误：记录每个炉子、每张卡的具体位置 → 对称性爆炸（炉不可区分、卡序无关）
✓ 正确：按维度聚合
  - 各任务类型已完成数量（依赖层级 × 任务种类）
  - 空闲资源（main_free, steal_free, change_cur, store_cur）
  - 在制品（in_use[] + 剩余 tick, pending[]）
  - 当前阶段（主炼 / 囤货 / 切换过渡）
```
- 状态去重：规范化 key（多集合排序、资源池化），避免同义状态重复展开。
- 这避开了文档 A 的"全状态 BFS DP 表（50 张 2GB）"反模式——我们的 `sched_dp` 是轻量递推，不枚举全状态。

## 6. 偷炉白炼感知（StealAudit）

> 用户约束：偷炉只能炼 40 卡，**可能被好友收走白炼**。当前引擎无感知（只会下一 tick 静默重炼、再烧一次源卡）。

- 借炼提交时记 `(friend, target, 期望收取时刻)`。
- 下 tick 发现 `target` 不在炉里 → 判定"被收走 / 白炼"，计入统计。
- **换友策略**：优先借"不常收卡"的好友（按历史白炼率排序）。
- 借炼的 40 卡仍计入 `keep_ids` 保护（不被卖）。

## 7. 残留风险（诚实标注，未覆盖）

1. **"钉死"占位卡**：长期活动 / 高面额收藏卡不在 `keep_ids` 内也占箱。准入按峰值预留时若箱被钉死占满 → 可行子集算出"啥都塞不下" → 只能告警（硬约束，非引擎能解，需人清理）。架构给出口但不自动处理。
2. ~~**DP 尚未建模箱约束**~~ → **已实现（2026-10-24 验证）**：`sched_dp` 箱容量已是搜索状态维度（`box_cap` 落箱剪枝），不再是「先补箱约束才能 dispatch」的前置阻塞；DP 状态按「消耗时间轴」收敛（取卡/买卡入箱、精炼净腾 2 格、完工落箱全在状态转移内），非静态满箱快照。多套 bench 实测 DP 峰值箱顶格 216/218 运行、全程 0 溢出、0 买失败（详见 `engine_v2_仿真报告.md` 末节）。同轮修复了让 DP 值可信的四个求解器 bug（返回值漏 `t_rel` 致幻影最优、memo 后缀跨迭代混入、`rec` 库存恢复 `+=k` 致假证明、终局买卡丢失），修后「DP 值 == 模拟 makespan == 返回调度的模拟结果」全星阶成立。**DP 计划与滚动执行的 gap 仍是开放项**（见风险 6）。
3. **阈值 buffer 量化**：JIT 截止线 `top_remaining > feeder_chain + buffer` 的 `buffer` 取值只写了"保守"，需按"低层链总炉时 + 安全余量"反推，且要防延迟过头（顶层好了低层没齐 → 整套交不了）。
4. **重准入抖动**：箱动态空出 → 套被反复准入 / 踢出。需加迟滞（hysteresis）：准入后除非箱低于某阈值才踢。
5. **付费捷径的诚实失败态**：箱 + 保险箱都放不下 P0 低层料 → 顶层已买但整套交不了。引擎必须明确告警「顶层已收但箱满无法炼低层，需手动腾位」，**不静默空转**。
6. **DP 静态序与滚动执行的 gap（2026-10-24 量化）**：求解器修复后单套 DP 全星阶胜贪心（−1.95~−5.70h），但多套高星场景 DP 静态骨架追不上现实变化——3套(3+4+5★)·各3轮 控制器重解 **9591 次**（同规模低星场景仅 166 次），总时长仍慢 50.79h；机制与 2026-10-23 联合 DP 实验结论一致（物流延迟 + 跨套料争抢 + 轮内序过时把静态优势放大成劣势）。**紧箱饥饿变体（同轮实证）**：60 格·各2轮 DP done=0/4——静态 makespan 最优把箱顶到 60/60，滚动执行时买卡闸被 reserve 吃光 → 饿死（分岔性：同代码两次运行「流动/饿死」两态）；DP 路径缺 Step4 的 BoxCompaction（腾箱手段）是根因。当前缓解=承诺点重解 + LDS 截断 anytime 语义 + streak 等待过滤/退避 + 箱闸死锁兜底扫描；根治方向未定（DP 实例箱容削峰余量 / 箱死锁检测+卖 10 面底卡腾位 / 箱压过高回退贪心路径）。

## 10. 架构原则总结

1. **单一滚动重规划器**：不维护离线排产表（实测已证无优势 + 有同步复杂度）。
2. **聚合而非枚举**：消解对称性，避开全状态 BFS 爆炸。
3. **DP 按需介入**：多套争箱 + 高星才调 `sched_dp`；单套宽裕 / 1★ 走贪心快路径。**既不永远贪心，也不热路径搬重 OR。**
4. **决策与执行分离**：Planner 纯函数无副作用，Executor 纯 API 无决策；人干预被"每 tick 重读"吸收。
5. **卡箱是可回收资源**：优先"减少卡数"的动作（级联买 / 压实），而非"增加卡数"（买料）。
6. **不卖高值卡铁律**：腾箱优先级兜底也只卖 10 面底卡，高值卡只合 / 只挪。
7. **诚实失败态**：硬约束（箱 + 保险箱满）必须明确告警，不静默空转。
8. **离线求解 ≠ 在线引擎**：`sched_cmp` 是评测工具，不是 tick 组件。
