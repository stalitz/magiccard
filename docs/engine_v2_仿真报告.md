### 单套（1~5星，含多轮 / 无限炼）：✓ 通过

- 各星空箱起步独立炼成目标轮数；多轮连续交付无死锁、无溢出、无买卡失败；4★ 无限炼 375h 稳定产出 4 轮（炉占 90.8%），证实「collect→立即产下一套」管线正确。

- **峰值箱占用的正确口径（2026-10-22 应质疑重推）**：旧版峰值 166~201/218 是**仿真假象**——Step5 把 net_plan 的整套底卡需求（4★ 高达 176 张）一次性列入 emit_set，只限每 tick 买速（buy_cap≈13）、不限总量，箱里早早囤齐全部底卡等炼；实测峰值时刻 201 张中 176 张是底卡（94%）。同轮还发现并修复 **DP 分支底卡泄漏**：DP 投炉对底卡跳过 slot 分配 → `_do_refine` 收不到底卡 slot → 底卡永不进炉、全部泄漏囤积（实测 4★DP@800tick 炼 17 次却残留 164 张未耗底卡），已改为与贪心分支同口径。

**多套关键修复（3套 [60,59,62] 此前「完成 1 轮后卡死 74553 tick」的根因）**：

1. **AdmissionControl 过度预留**：旧版按 `sum(runs)` 给 P0 静态预留箱位，但精炼**净腾 2 格**（耗 3 喂料 / 落 1 张）根本不长期占箱——等于预留了个不存在的压力，把其余套全 defer，而 P0 自己缺底卡又炼不动 → 全局停转。现改为「凡有净需求（runs>0）即准入」，箱位安全交给 Step5 买卡节流 + 精炼净负占用保证。

**本轮修复（2026-10-22，回应用户「峰值不可能=把全部底卡买齐等炼」的质疑）**：

1. **JIT 拉动买卡**（替代表面积）：`due` = 即将能炼的合成卡（非底卡喂料全在箱/炉）的实例底卡喂料 + collect 在即的收藏底卡；depth-1 全底卡喂料首 tick 即拉动、上层随中间卡落箱逐层获得。实测 bought 从「超买+卖卡churn」变为**回归理论需求**（多套场景分毫不差），峰值箱 4★ 196→60、3★→44、5★→26、多套 214→68~84、紧箱 74→49/59。

2. **DP 分支底卡泄漏**：DP 投炉分支对底卡 `continue` 不分配 slot → 底卡永不进炉、泄漏囤积（4★DP@800tick 残留 164 张）。改为三种喂料一视同仁（底卡同样占箱位、同样被消耗），与贪心分支口径对齐。

3. **单套超标不停机**：旧版只查「全部达标」才停，已达标的套继续炼下一轮 → 占炉/囤箱、拖慢未达标套，还虚增 bought/refined（实测 2套·各3轮 4★ 被多炼 40 次=部分第4轮）。现按套达标即退出调度，完成轮数精确达标、bought 分毫不差。

4. **喂料半途失败回滚**：投炉时喂料取到一半失败（后一个喂料缺失），旧版已扣的 `stock_avail`/`taken` 不恢复 → 同 tick 后续投炉被误跳。现回滚后同 tick 口径准确。


**DP 求解器修复（上一轮）**：`sched_dp.solve` 的 `time_budget` 守卫原用 `time.time()`，在本测试环境的钟被 mock 成乱值导致预算失效、单次 DP 解算搜满 800 万节点烧 ~57s；改为 `time.perf_counter()` 后守卫稳定生效，单次解算锁定在 2.0s（~30 万节点、`bounded=True`），引擎端 `dp_plan` 又改为只解一次复用，彻底消除每轮重解开销（4★×3 轮从「墙钟 390s+ 且疑似卡死」降到 27s 干净跑完）。


**已知取舍**：贪心路径喂料半途失败回滚后，「浅层卡抢走深层卡喂料」的现象得到真实暴露（旧版的泄漏意外保护了关键路），4★ 贪心因此慢 ~3h（95.39 vs 旧预买口径 92.05）；DP 路径不受影响（单套高星生产路径）。JIT vs 预买整体占优（3★/5★ 更快、峰值减半、零浪费），后续可考虑「保护即将 priming 的深层卡的喂料」进一步优化贪心。


**多套 DP 接线评估（2026-10-22，回应「DP 价值是否真体现」的追问，全量数据见 `tests/_exp_rules.py`）**：

1. **套内排序键两度实测否决**：① cp 关键路序仅单套 3/4/5★ 有效（76.06/84.06/173.11 vs 贪心 82.74/95.39/184.51），多套共享箱时把单链卡前置→互抢枢纽喂料（同 tick slot 争用 ×9、完全空炉 tick ×3.5，2套·各3轮 412→430h）；② 按套 DP 序（dp_orders 接线）共享段同样负（2套 +8h、3套 +27h）——DP 模型按 3 炉独占求解，与共享 reality 不符。均回退，planner 留有注释。

2. **尾部 DP 是正解**：`len(active)==1`（先达标的套退出后最后一套独占资源）时自动激活 DP 分支，3套·各3轮 475.8→467.8h、2套 424.9→412.2h。

**买卡节流修复（2026-10-23，回应「含 5★ 组合炉占塌」质疑）**：

- 现象：含 5★ 组合炉占均值 79.6% vs 不含 5★ 87.7%，并行收益从 ~10% 塌到 ~4%。

- 根因探针三连（修正了初版在 decide 之后采样、场景没跑完的坏探针）：v3 按「决策时空闲炉 × 在跑套数」分桶，确认 **62.8% 空闲发生在 ≥2 套仍在跑时**（物流 starvation，非异构尾效应）；分类探针进一步确认这些空闲 tick 里**缺料 feeder 卡 98% 是「根本没买」、仅 2% 在途**——是真·买卡没跟上，非结构性 pipeline 深度。

- 但本修法**对 5★ 组合几乎无效**（3+4+5★·各3轮 84.2→84.6%、1+4+5★ 还微退）：5★ 套顶层 42.5h 长烧，3★/4★ 套各自 66h/90h 就跑完 3 轮，剩下 ~800h 仅 5★ 独自 grind——这是**异构 makespan 尾效应（固有）**，且真能救的并发阶段瓶颈不在 `buy_cap` 而在 `due` 仅 1 层深（深层 feeder 不在 `due` 里，抬高买量也买不到）。要动 5★ 尾须改 `due` 为 2 层前瞻（拉喂料的喂料），但有撑箱风险，待定。

- 结论：本步修法方向对、零回归、无溢出，但**没解决 5★ 尾效应**；其剩余价值在「按套延迟 P0 反转（高星先交付）」，不在买卡或 makespan-DP。

## 求解器修复 + DP 控制器全量 bench（2026-10-24）

背景：`sched_dp` 求解器被发现有系统性错误（memo 值偏小、调度记录丢失），本轮修复后重做全量验证。所有「DP 值」均由**独立调度模拟器**复算（`tests/_verify_sched.py`：素材开工扣减、完工入箱、箱容 218、按机器类容量检查——买卡 op 占 shop 不占炉位），不接受求解器自报值。

### 1. 修复的求解器 bug（5 个，全部有实测证据）

1. **返回值漏 `t_rel` → 幻影最优**：`dfs` 在 while 循环内「收卡/推进到下一完工」耗掉的时间没计入返回值（memo 存的是偏小的相对值）。1★ 实测 root=6.03h < 真实 7.03h，且违反自身总炉时下界 6.5h；关掉 memo 值即恢复 7.03h → 定位 memo 值被污染。旧代码答案正确纯属叶子赋值 `best["val"]=t+fin`（绝对值口径）侥幸。
2. **`rec` 库存恢复 `st[j] += k` 应为 `+= c*k`**：c≥2 时库存被污染 → 极大向量枚举不完整 →「bounded=False 证完最优」是假证明（4★ 全量跑 82.05h"最优" vs 截断跑实找到 78.05h；修复后 2★ 从 22.02h 变 23.02h，旧值是 bug 喂出的假优解）。
3. **买卡 op 记录时刻丢失**：买卡只在分支点记录，「无向量可开→推进时间」分支 `continue` 时整体丢弃 → 1★ 实测 t=0 的买卡全被记成 t=45s，执行层时序全错。
4. **memo 调度丢失（两连）**：① memo 命中跳过叶子 → 最优调度永不被记录（改为 memo 存 `(值, 后缀链)`、根后缀重建）；② `link()` 实现 bug——`cells[-1]` tail 修改被重建循环首轮覆盖，子树后缀每次被甩掉（64→31 ops）。
5. **memo 后缀跨迭代混入**：memo 键是迭代顶状态（前序买卡已入状态），但后缀若含全部 own_ops 会重放前序买卡 → memo 存「本迭代顶状态起」的后缀、返回存「调用入口起」的后缀（双链）。

另修 **INF 不落 memo**：LB 剪枝产生的 INF 依赖当时 `best["val"]`（绝对口径），不是状态纯函数，存入会让后续以更紧 UB 访问同一状态时被幻影 INF 挡住。

5. **箱闸死锁兜底扫描**：本 tick 零精炼时，全量扫第一个「到期+喂料齐+有空炉」的 refine op 发掉（每 tick 最多 1 个、记 discrepancy）——解「cursor 卡在成串发不出的 buy op 上、扫描窗口够不着箱内 trio」的死锁（60 格实测 tick 10000：99 个 buy 堵头、箱内 157×6 等 trio 在窗口外）。

## JIT 门 + 腾箱：紧箱饥饿根治（2026-10-25）

背景：上一轮记录「紧箱 60 格·各2轮 DP done=0/4 未修复到验收」——DP 静态 makespan 最优把箱顶到 60/60 → 买卡闸 `box_free - reserve` 被吃光 → 头 op（buy）永发不出 → cursor 冻结饿死（全程槽占 21.5%，同代码两次运行轨迹分化 93.6% 流动 / 21.5% 饿死）。本轮做机制级根治。

### 1. 根因：执行层买卡无 JIT 纪律（囤货）

pass 1 旧版 reactive 买卡「扫描到就买、不等计划时刻」只受**箱预算闸**约束——宽箱（218）下表现为把整套底卡需求一次性买齐（4★ 峰值 201/218、94% 是底卡，正是 2026-10-22 已实锤的「囤齐全部底卡等炼」仿真假象）；紧箱（60）下箱被喂料囤到硬顶，买卡闸吃光 → 饿死。DP 骨架本身带箱容约束（静态投影不超 60），是**执行层把未来 buy op 提前拉齐**打破了投影。

### 2. 修复一：JIT 门（`_jit_due` + pass 1 门禁）

- **due（同贪心 Step-JIT 口径）**：遍历骨架未发 refine op，「非底卡喂料已齐（可炼）」的合成卡 → 其实例底卡喂料毛需求。depth-1 全底卡喂料首 tick 即拉动，上层随中间卡落箱逐层获得，天然 JIT。
- **门禁**：喂料底卡只在 `箱内 + 炉内 + 本 tick 在途 < due` 时放行买卡 op（即买即用，不超买）；op **不标记 issued**——前沿需求后续增长时再放行。纯收藏底卡（不喂任何合成卡、无精炼消费者）不走门，由专辑预买/计划终局 op 按 collect 在即拉起。
- 与旧 reactive 纪律的关系：保留「不过 start 时序门」（避免消费者等落箱 1~2 tick 的空转），只把「买量上限」从箱预算改为 **due ∩ 箱预算**。

### 3. 修复二：腾箱（`_box_compaction`，同贪心 Step4 口径）

箱紧（`change_free <= 2` 或 `box_free <= 4`）时：① **卖多余 10 面底卡**（双箱，保留 `max(1, due)` 张；铁律——只卖 10 面、高面值卡与 40 面素材绝不卖，10 面卡 sell_card 只换回面值等额金币故卖+买无损；同步回减 `plan["bought"]` 去重账）；② **挪多余合成卡进保险箱**（保留未发 op 喂料需求，预测 sim 首空位规则并修 `avail_slots` 防悬空槽位）。sell/move 动作排在 buy 前，executor 按序执行 → **腾出的位当 tick 即可被买卡用上**。每次腾箱记 1 点 discrepancy（计划与现实偏差信号 → disc_over 重解）。

## sched_dp 轮转买 + 落位保留：紧箱 DP 层根治（2026-10-25）

### 1. 根因：DP 约束解结构性死亡（两层）

JIT 门修好执行层后，紧箱 60 格·各2轮 仍 FAIL——逐 tick 探针（`_probe_deadlock` 26000 tick）实锤根因在 **DP 求解器本身**：

- **dfs lazy 买卡无落位保留**：只校验「箱内+在途 < cap」，确定性把箱囤到顶 → 在炉产物落箱即超容（`sum(ns) > box_cap` → 分支 INF）→ 所有分支 INF → root 返 INF → `box_relaxed=True` 无约束重解 → 静态投影箱峰 88/60（超 60 格硬顶）。
- **不对称即根因**：`_ub_schedule` 早有落箱时刻投影（`proj = box_used + 落箱炉数`），dfs 侧漏了同口径保留。
- **UB 死锁保护无箱检**：`_ub_schedule` 的「无进展即强买」分支不校验箱容，进一步放大超容。

### 2. 修复：轮转买 + 落位保留（dfs 与 UB 两层同口径）

- **落位保留**：不变量「箱内 + 在途买卡 + 在炉产物 + 本 buy ≤ box_cap」——买**前**校验买**后**占用（旧版 `box_used < box_cap` 是差一错误：买后实占 cap+1）。不变量被全部迁移保持（买卡买前校验、落箱 ±0、精炼开工 -(k-1)）→ UB/约束解箱容可行。
- **轮转买**（对齐贪心 2026-10-23 实锤纪律）：每轮每种需求类型各买 1 张。旧版按类型序把一种买到需求上限（如 231×24 买完才买 230）→ 箱被单类型塞满 → 3 合 1 trio 永远凑不齐 → 无精炼可开 → 死锁（正是贪心侧修掉的「多套死锁另一根因」，DP 同款）。平衡采购让 trio 尽快成型、被精炼及时消耗、箱位滚动释放。
- **效果**：紧箱 DP makespan 376.86h → **162.35h**（优于贪心 181.49h），两套底卡首 tick 起交错，首个 refine 提前到 op30；求解器复验全过（1★ 7.04 / 4★ 78.69 / 5★ 164.81h，DP 值 == 模拟值）。

## 4★ 回归根治：vec_prio 改向上 cp（2026-10-25）

### 1. 现象与定位

轮转买上线后 4★ 单套回归 78.15→84.08h。逐 tick 全量 trace（`_probe_4star_full`，钩 `decide` 覆盖 skip tick）实锤：

- **隔离测试**（`_probe_solver_iso`，同 t0 instance 新旧代码对照）：旧代码 UB=86.04h 但**搜索挖到 78.05h**（188×3@t4）；新代码 UB=83.35h（轮转买改善 UB）但**搜索只到 82.04h**。20s 预算也卡 82.04h——不是预算问题。

### 2. 根因：向量启发式是「向下 cp」，叶子卡全打平

**结论（前 8 例）**：单套 1~5★ DP 全面优于贪心（1.97~4.94h，4★ 反超 HEAD 基线 78.81→77.45h，验收红线收回）；2套·各1轮中 (4+3)/(4+5) 两例 DP 略慢贪心 ~1.5~2h（静态骨架+滚动重规划的 known gap，done 达标、零溢出），(1+5) DP 快 9.08h（1★ 套被 5★ 长炉占用，DP 调度更利）。全部 0 买失败、0 错误。后 2 例（各3轮压力测试）为聚焦紧箱修复已主动 kill，作 follow-up，非验收红线项。

## sched_dp 离最优有多远：CP-SAT 精确对照（2026-10-25）

### 为什么必须做这件事

此前所有验收都是**相对**的：只要「比贪心快」「比 HEAD 不退化」就收工。
从不知道**离真最优差多少**。`_verify_sched` 验的只是**自洽**（DP 值 == 独立模拟器复算值），不是最优性。
`stats.bounded` 只是「搜索预算内没被剪枝打断」，不等于证明了最优。

`backend/engine_v2/tests/cp_sat_solve.py` 用 **OR-Tools CP-SAT** 建作业级
RCPSP-with-materials 精确模型，第一次把「差多少」量出来。

### 模型（买/炉/偷炉/物料在同一个状态空间）

- 每个卡种 i 建 `need0[i]` 个作业实例，`start/end/dur` 为决策变量。
- **机器容量** `AddCumulative`：主炉 3 / 买卡 15 / 偷炉 1，互不抢占。
- **40 面卡（class 表 `[0,2]`）**：mode 二选一（主炉 or 偷炉），共享 start/end（optional interval）。
- **物料**：作业 (i,u) 需 `mats[i]` 中 k 张 j → assignment boolean `use[(i,u),(j,v)]`；
  每张 j 产出至多被一个消费者用；`use=1 ⇒ end[j,v] ≤ start[i,u]`。
- **目标**：min makespan = max end。
- 时间单位 = 该 instance 全部 dur 的 **gcd**（1★/2★ = 45s，3★+ = 15s）。

> 这就是「买卡、腾箱、选炉、合成全在同一个状态转移里」的形态——
> 不是拆成模块各自贪心。CP-SAT 不遍历状态空间（填表 DP 在 4★ 联合状态 ~10²⁶ 不可行），
> 它靠约束传播 + 分支定界求解同一个 MIP。

### 五全星对照（iso 同 t0 instance，双验证通过）

| 星 | sched_dp（生产 2s 预算） | CP-SAT | CP-SAT 状态 | bound（真最优上界） | **sched_dp gap** |
|---|---|---|---|---|---|
| 1★ | 7.04h | **7.01h** | **OPTIMAL 11s** | 7.01h（已证） | 0.4% |
| 2★ | 26.02h | **22.01h** | FEASIBLE 180s | ≤20.02h | **18.2%** |
| 2★（30s 预算） | 25.02h | 22.01h | 同上 | 同上 | 13.7% |
| 3★ | 72.69h | **67.35h** | FEASIBLE 180s | ≤66.68h | 7.9% |
| 4★ | 78.69h | **73.35h** | FEASIBLE 240s | ≤72.90h | **7.3%（5.34h）** |
| 5★ | 164.81h | **164.28h** | FEASIBLE 240s | ≤162.72h | 0.3% |

验证方式：CP-SAT 解必须过 `precise_check`（按实际 mode 的事件扫描，权威容量）
+ `simulate`（物料 + 箱容）双重复算，全部 `可行=True` 且 makespan 一致。

### 三个必须记住的结论

**1. 「1★ root=7.04h 证最优」是假象。**
CP-SAT 11s 证出真最优 7.01h（低 2 tick）。sched_dp 的可采纳下界不紧，
**在界内自证了一个错误的最优值** —— 所有「root == DP 值 ⇒ 最优」的结论都不可信。

**2. gap 不单调，最差在「宽而浅」，不在高星。**

| 形态 | 代表 | gap |
|---|---|---|
| 宽而浅（ready 集宽、组合爆炸） | 2★ 18.2% / 3★ 7.9% / 4★ 7.3% | **大** |
| 深而窄（单卡长链锁死 makespan） | 5★ 0.3% | 极小 |

5★ 单卡 2453 tick 长链把 makespan 钉死，调度自由度本来就小；2★~4★ ready 集宽，
anytime 2s 截断根本撞不到好解。**所以「堆 LDS / 向量指路救高星」一直是打偏的靶子**。

**3. 「2★ 不如贪心」这个说法，方向对、结论错。**

| 星 | 纯贪心（列表调度 UB） | sched_dp 2s | CP-SAT | 判读 |
|---|---|---|---|---|
| 1★ | 9.01h | **7.04h** | 7.01h | DP 赢 1.97h |
| 2★ | 27.01h | 26.02h | **22.01h** | DP 赢 0.99h；**两者都远离最优 4~5h** |
| 3★ | 78.68h | **72.69h** | 67.35h | DP 赢 5.99h |
| 5★ | 178.82h | **164.81h** | 164.28h | DP 赢 14.01h |

- 纯贪心**从来没有**真正赢过 sched_dp（旧版「2★ 贪心反赢」用的是引擎级贪心控制器口径，
  与 iso 求解器口径不同，且差异落在调度噪声量级内）。
- 但更要紧的是：**贪心 27.01h、DP 26.02h、真最优 22.01h** —— 争「谁赢 1h」
  毫无意义，两个都差 4~5h。**缺 gap 意识的比较，只是在噪声里排座次。**

### 方法论复盘

| 问题 | 后果 |
|---|---|
| 把 DFS+LDS+2s 强停命名 `sched_dp` / 「DP」 | 名字一错，后面所有「DP 最优」讨论都建在假前提上 |
| 买卡/腾箱/选炉/合成拆成独立模块各自贪心 | 90% 决策不在统一搜索里，DP 只排「合成顺序」 |
| 只用相对指标（vs 贪心、vs HEAD），无 admissible 下界 | 不知道离最优多远，容易为 0.5h 反复打补丁，却漏掉 5h 的真 gap |
| 优化方向靠现象驱动（vec_prio/JIT/腾箱逐个补） | 靶子打偏：把力气花在 5★（gap 0.3%），真正的弱点是宽 ready 集（2★/3★/4★） |
| 任何要「该不该换工具」的判断，先做备选比较 | CP-SAT 一个模型 11~240s 就把五全星 gap 全量出来了，比反复调启发式便宜得多 |

### 已踩的坑（务必记住）

1. **时间单位必须取 gcd**：固定 `TICK=45` 会把 24000/81600/152880s round 掉 15s，
   CP-SAT 认为卡提前完成 → 与真实 dur 不一致 → 假报「主炉超容 4>3」。
2. **`simulate` 会保守误报容量超限**：它拿不到 `[0,2]` 的实际 mode，只能必要条件检验；
   CP-SAT 解的容量以 `precise_check`（按真实 mode 事件扫描）为准，`simulate` 仍负责物料+箱容。
3. **CP-SAT 精确最优只覆盖 1★**（11s 证完）；2★–5★ 是 180~240s anytime 可行解，未证最优，
   但已全线优于 sched_dp。

### 生产化的约束（诚实结论）

CP-SAT 单次求解 180~240s，**不可能每 tick 重解**。可生产化的形态只有一种：
**离线/冷启出全局骨架 → 喂 `dp_controller` 滚动执行**（偏差时用 2s 的 sched_dp 补解）。
其收益必须实测——引擎层的 JIT 纪律 + 滚动重解会吸收一部分调度优势，
iso 的 gap 不能直接搬成引擎级收益。

## A 步：CP-SAT 冷启骨架接引擎（2026-10-25）——负结果，不上生产

### 实验设置

`sched_dp` 求得的骨架已证明差真最优 7~18%（iso 口径），于是按「离线出界 + 滚动执行」
把 CP-SAT 接进 `dp_controller`：

- 新模块 `backend/sched_cmp/cp_sat_plan.py`：与 `sched_dp.solve` **同契约**
  （返回 `mk, sched, stats`），`_solve_plan` 里只要把 `sched` 换成它产出即可，
  ops 构建逻辑完全复用（backend-agnostic）。
- 开关：`MC_CP_FIRST=1`（+ `MC_CP_BUDGET`），默认关。
- 触发条件严格限定：**仅第一个承诺点** + 空箱 + 空炉 + 空 memo（CP 模型只支持冷启）
  + 箱容不瓶颈（`Σneed0 ≤ box_cap`，CP 不建模箱容，峰值上限=总张数）。
  后续偏差重解仍走 `sched_dp` 2s 快路径（CP 单次 180s 进不了每 tick 循环）。

### 结果（单套·2星，同 bench 口径）

| 方案 | 计划 makespan（iso） | **引擎级实际** | 执行损耗 |
|---|---|---|---|
| 贪心 | — | 28.04h | — |
| sched_dp 骨架 | 26.02h | **23.05h** | **−2.97h（执行层反而更好）** |
| CP-SAT 冷启骨架 | **22.01h** | 24.12h | +2.11h（执行层吃掉全部优势） |
| CP-SAT 骨架 + JIT 门宽箱放开 | 22.01h | 24.07h | +2.06h |

CP-SAT 的最优骨架**执行后比 sched_dp 慢 1.07h**。诊断（`_probe_cp_diag.py`）：

```
CP stats: FEASIBLE mk_tick=1761 (22.01h) bound=1602t (20.02h)
执行统计: solves=2 jit_blocked=9272 emerg=0 disc=14 buy_failed=0 peak_box=37
```

`jit_blocked=9272` 说明：CP 最优解靠 t0 起用满 15 个买卡位连续买入 80 张底卡
（pipelining），而执行层的 JIT 门把它全拦下 → 骨架 t0 的精炼 op 无料。
试过「JIT 门只在箱紧时生效」（`box_free < Σdue` 才严格，否则按 3×due 放宽）：
`jit_blocked` 消失、基线 23.10→23.05h（**噪声级**），CP 侧 24.07h 仍无改善。

### 根因（第三次独立复现同一条规律）

**静态紧排产 ≠ 滚动可执行的排产。**

- CP-SAT 给的是**零容差**最优序：每一张卡的 start 都卡死在临界时刻，
  任何物流延迟（买卡 LAG、喂料 1~2 tick 迟到）都无法吸收 → 整链后移。
- sched_dp 给的骨架**松**（26.02h vs 22.01h，多 4h 余量），执行层用
  reactive 买卡 + 有限偏差扫描把余量收掉，**实际 23.05h 反而优于自己的静态解 2.97h**。
- 所以「引擎 vs 最优」的真实差距远小于「求解器 vs 最优」：
  **executor 的容忍度本身是一层优化**，静态最优把它浪费掉了。

这与既有实锤同源：`joint_dp` 静态联合最优序接滚动引擎**反输 22~40h**（2026-10-23）。

### ★ 关键校正：真实的交付层 gap（不是 18%）

上文 iso 表度量的是「**求解器** vs 最优」，不是「**引擎** vs 最优」。校正后：

| 星 | 引擎级实际（sched_dp） | CP-SAT 最佳已知 | **真实 gap** |
|---|---|---|---|
| 1★ | 7.08h | 7.01h（已证最优） | 1.0% |
| 2★ | 23.05h | 22.01h | **4.7%** |
| 3★ | 71.44h | 67.35h | **6.1%** |
| 4★ | 77.45h | 73.35h | **5.6%** |
| 5★ | 164.86h | 164.28h | 0.35% |

- 交付层面差 **0.4%~6%**（1★ 约 4 分钟、3★ 约 4h），不是 iso 表的 18%。
- 另有一处口径差须记住：引擎每 tick 买卡上限 = `炉数×3+6`（4 炉 = 18），
  而 iso 模型 `shop_cap=15` → **iso 比引擎更紧**，iso 值不能当引擎下界
  （这也是引擎 23.05h 能低于 iso 求解器值 26.02h 的一部分原因）。

### 结论与定位

| 用途 | 采纳? | 理由 |
|---|---|---|
| CP-SAT 当**生产骨架来源** | ❌ 不采纳 | 紧排产无容差，引擎级反输 1.07h（2★ 实测） |
| CP-SAT 当**最优性标尺 / gap 度量** | ✅ 采纳 | 离线 11~240s 就能算出「离最优多远」，是唯一可信的 ground truth |
| CP-SAT 当**规则挖掘工具** | ✅ 采纳 | 对比 CP 最优解与引擎轨迹，可定位系统性错误（如买卡并行度、优先序） |

代码保留 `cp_sat_plan.py` + `MC_CP_FIRST` 开关（默认关），作为后续对照实验的入口。
